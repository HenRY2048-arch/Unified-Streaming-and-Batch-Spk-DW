# A 组（实体与维表）形态草案（v0.1 · 待评审）

> 配套：`Generator_Refactor_Checklist.md`（A 组）、`Event_Contract_Draft.md`

> 日期：2026-10-16

---

## 0. 范围

覆盖改造清单 **A1–A5**：作者实体、作者产出、有限有向图、图与内容耦合、以及"边由旅途产生"的红线。

---

## 1. 实体关系（ER 形状）

```
           产出 (1..*)
  User ───────────────────► Item
    ▲ │                      ▲
    │ │ 关注 (有向边)         │
    └─┘                      │
    │                        │
    └──── 行为 ──────────────┘   (曝光 / 点击 / 消费 / 互动)
    │
    └──── 行为 ──► User        (关注 / 取关 / 私信 / 进主页)

  Session：把一次会话内的行为串起来（行为自带 session_id）
```

- **User**：既是读者，也可能是**创作者**（见 §2）。
- **Item**：归属某个 User（`author_id`）→ 使"关注流"能连到内容（A4 的硬前提）。
- **Follow**：User → User 的**有向边**，是图；也是"关注流"的来源。

---

## 2. 关键决策点：作者是否就是用户？

| 方案 | 说明 | 后果 |
|---|---|---|
| **甲（建议）** | **作者 ≡ 用户**：创作是用户的一种能力/角色，**一个 ID 空间** | 关注边**直接**决定"关注流"的内容来源（A4 成立）；无需两套实体/两套 ID；与微博一致 |
| 乙 | 作者是**独立实体**（只有创作者发内容，普通用户只消费） | 关注图与内容**脱节**——"关注流"没有内容可派（除非再建"用户→作者"关系）；多一套实体 |

**建议采纳甲**。若采纳，则**不需要 `dim_author`**，改为在 `dim_user` 上增加"创作者"属性。

---

## 3. 实体与维表清单

| 实体 | 键 | 属性（草案） | 变化性 | 落地形态 |
|---|---|---|---|---|
| **User** | `user_id` | `interest_tags`, `level`, + **创作者属性**（`is_creator` / 领域 / 活跃度「待定」） | 基本静态 | `dim_user_profile.csv`（**种子**） |
| **Item** | `item_id` | `author_id`, `category`, `tag(s)`, `content_len`, `published_ts` | **会新增**（作者产出） | 初始池**快照** + 新增**走事件** |
| **Tag / Category** | tag / category | 两级分类（沿用旧字典） | 静态 | 内置于配置 |
| **Follow edge** | (`follower`,`followee`) | `ts` | **会增删**（低频） | 初始**种子快照** + 变更**走事件** |
| **Session** | `session_id` | user、起止 | 运行期 | **不落维表**（事件自带） |

---

## 4. 图的形态

- 节点 ＝ **用户**；边 ＝ **有向关注**（`A → B` 表示 A 关注 B）。
- **规模**：**有限**（用户数 N、平均出度 d「待定」）。
- **种子**：一次性生成。模型「待定」——随机图 / 优先连接 / 分群；
  建议"**分群 + 优先连接**"，让图有真实社区的簇状结构。
- **演化**：**只由 `follow/unfollow` 事件增量改边**，不跑独立演化模型（红线 A5）。
- **对外暴露**：**初始边快照 + 变更事件**；T 层可据此重建"任意时刻的边状态"。
- 生成器内部另维护一张**内存图**（分发要用），但**对外不暴露内部状态**。

---

## 5. 作者产出的形态

- 作者按速率产出**新内容**（`item_id / author_id / category / tag / content_len / published_ts`）。
- 形态：**产出即事件**（建议新增 `item_published`，走 Kafka），而非只改快照。
- 于是 `dim_item` 成为**只追加的缓慢变化维**（首次出现即插入）；
  **建议 append-only，不做 SCD2**——除非将来允许 item 属性被修改（「待定」）。
- 初始内容池仍以**快照种子**给出（t0 的存量）。

---

## 6. 维表"变更"如何暴露给 T 层（**重点待商榷**）

| 路线 | 做法 | 适用 |
|---|---|---|
| (a) 快照重写 | 生成器定期重写 CSV/parquet，T 层每 micro-batch 重读（＝现状的热更新） | **静态实体**（用户 / 标签） |
| (b) 变更走事件 | 新增/变更以事件进 Kafka，T 层从事件**增量维护**维表 | **动态实体**（item 新增、关注边） |

**建议：静态走 (a)、动态走 (b)**——一刀切都不合适。（这条直接影响 T 层怎么维护维表，请重点确认。）

---

## 7. 图与内容的耦合（A4）

- **关注流**候选 ＝ **被关注用户**产出的（近期）内容 → 需要 `author → items` 的**反向索引**。
  → 因此 **`item.author_id` 是 A4 的硬前提**。
- **探索流**候选 ＝ 全量内容池。
- **推荐流**候选 ＝ 按 `interest_tags` / 分类匹配到的内容池。

---

## 8. 待定 / 待商榷

1. **作者 ≡ 用户**（建议甲）？
2. 图规模 **N**、平均度 **d**、**种子模型**（建议"分群 + 优先连接"）？
3. 维表变更的暴露方式（§6，建议"静态走快照、动态走事件"）？
4. `dim_item` 是否**严格 append-only**（是否允许 item 属性被修改）？
5. **创作者属性**具体包含什么（`is_creator` / 领域 / 活跃度 / 影响力）？

---

## 9. 红线

- **边由旅途产生**；生成器对外只暴露"**种子 + 事件**"，不暴露内部图状态。
- **`item.author_id` 必须存在**（A4 的硬前提）。
