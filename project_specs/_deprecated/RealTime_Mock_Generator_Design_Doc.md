## **一、 需求背景**
本项目旨在为“小红书式”内容社区实时数仓提供高质量的无界流数据源。通过 Java 脚本模拟真实的用户交互行为，产出符合业务逻辑、包含时间语义、且具备数据质量挑战（乱序、异常）的 Mock 数据。

## **二、 核心设计目标**
1.  **业务逻辑高仿真**：模拟 13 种真实社区行为，实现“70% 兴趣匹配 + 30% 探索”的分发逻辑。
2.  **时间语义完备**：严格基于事件时间（Event Time）生成数据，注入 10% 的乱序延迟（30-60s）。
3.  **会话状态追踪**：通过 `session_id` 维护行为连贯性，支持 `app_open` 触发及 30 分钟超时自动切换。
4.  **维度建模解耦**：遵循事实与维度分离原则，笔记与作者无创作关联，作者 ID 仅作为 IP 影响力信号。

## **三、 技术选型与架构**
-   **语言**：Java 8 (JDK 1.8.0_412)。
-   **消息队列**：Kafka (Topic: `content_events`)，采用单 Topic 多事件设计。
-   **维表存储**：本地 CSV (`dim_item.csv`, `dim_user_profile.csv`)，启动时加载至内存。
    -   **核心约束**：`dim_user_profile` 中的 `interest_tags` 为**静态种子画像**（每个用户随机分配 1-3 个标签），代表初始偏好，在实时处理链路中始终保持静态，不可变动。
-   **关键库**：`kafka-clients`, `javafaker`, `jackson`。

## **四、 数据契约 (Schema 设计)**
每条 JSON 消息采用“超集 Schema”设计：

| 字段名 | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- |
| `event_id` | String | 是 | 唯一 ID (`evt_{uuid}`) |

| `event_type` | String | 是 | 13 种事件枚举值 |
| `ts` | String | 是 | 事件发生时间 (ISO 8601 毫秒级: `YYYY-MM-DDTHH:mm:ss.sssZ`) |
| `session_id` | String | 是 | 会话 ID (格式: `sess_{ts}_{user_id}`) |
| `platform` | String | 是 | 终端平台 (`ios`, `android`, `web`) |
| `item_id` | Long | 否 | 笔记 ID (200001 - 200100) |
| `target_user_id`| Long | 否 | 目标博主 ID (关联 100xxx) |
| `duration_sec` | Double | 否 | 停留时长 (仅 `leave_item`) |

| `content_len`  | Integer| 否 | `50` - `5000` | 笔记长度 (用于计算滑动速度) |

### **2. 维表字段规约与种子分布算法**
为确保事实流与维表能够成功 Join，维表物理结构与生成算法定义如下：

#### **(1) `dim_user_profile.csv` (250 总量)**
- **物理结构**：`user_id` (Long: 100001-100250), `interest_tags` (String), `level` (Integer: 1-5)
- **分布算法**：
    - **覆盖率**：仅 **20% (50名)** 生成 `interest_tags`（1-3个随机标签）；其余 80% 留空。
    - **等级分布**：`level` 呈正态分布（L1/L5 各 5%，L2/L4 各 20%，L3 50%）。

#### **(2) `dim_item.csv` (100 总量)**
- **物理结构**：`item_id` (Long: 200001-200100), `category` (String), `content_len` (Integer: 50-5000)
- **分布算法**：
    - **类目分布**：5 大分类各分配 20 篇笔记，确保各频道热度数据均衡。
    - **长度分布**：`content_len` 在 `[50, 5000]` 间均匀分布，支撑滑动速度异常检测。

## **五、 核心业务逻辑与数据字典**

### **1. 13 种事件权重分布与字段填充规约 (Sum = 100%)**
| 事件分类 | 事件 (event_type) | 权重 | 字段填充规则 (除基础字段外) |
| :--- | :--- | :--- | :--- |
| **基础** | `app_open` | 3% | `item_id`, `target_user_id` 均为 `null` |
| **曝光** | `enter_item` | 40% | `item_id` 必填；`target_user_id` 为 `null` |
| **消费** | `leave_item` | 35% | `item_id`, `duration_sec` 必填 |
| **反馈** | `like`, `fav`, `share`, `dislike` | 17% | `item_id` 必填；`target_user_id` 为 `null` |
| **意向** | `dm`, `follow`, `unfollow` | 4.5% | `target_user_id` 必填；`item_id` 为 `null` |
| **辅助** | `click_tag`, `enter_profile`, `comment` | 0.5% | 前两者必填 `item_id`, 后者必填 `comment_text` |

### **2. 数据字典 (Enums & Corpus)**
#### **(1) 两级分类体系 (Category & Tags)**
- **时尚美妆**: [`美妆`, `穿搭`]
- **生活记录**: [`旅行`, `美食`, `宠物萌宠`]
- **知识成长**: [`科技`, `学习`]
- **身心健康**: [`健身运动`, `情感`]
- **家庭生活**: [`母婴育儿`, `生活方式`]

#### **(2) 语料库 (Corpus)**
- **评论内容**: ["写得真好", "学到了", "干货满满", "绝绝子", "收藏了", "踩坑了", "不太适合我"]
- **咨询内容 (dm)**: ["怎么买？", "链接有吗？", "多少钱？", "求私信资料"]

### **3. 核心算法**
- **70/30 推荐模拟算法**：
    -   **70% 兴趣匹配流**：若用户具有静态种子标签集合，脚本首先从该集合中**随机抽取一个标签**，随后从符合该标签的笔记池中随机抽样。这确保了多标签用户在 Mock 过程中展现出交叉兴趣的分布特性。
    -   **30% 随机探索流**：模拟兴趣漂移或系统探索，无视用户标签，从全量笔记池中进行均匀随机抽样。
    -   **冷启动处理**：对于无画像用户，100% 进入随机探索流。
- **状态机**：维护 `(user, item)` 的进入时间，在 `leave_item` 时计算 `duration_sec`。
- **异常注入**：为增强数据挑战，脚本需按以下规则注入异常：

| 异常模式 | 触发机制 | 行为序列逻辑 | 参数设定 |
| :--- | :--- | :--- | :--- |
| **A1 刷屏评论** | 全局计数器 `count % 1000 == 0` | 选中 1 名用户和 1 篇笔记，**连续发送 5 条** `comment` 事件。 | `ts` 每条递增 1s，`session_id` 保持一致。 |
| **A2 疯狂点赞** | 全局计数器 `count % 1000 == 500` | 选中 1 名用户，在 **5s 内** 对 15 篇不同笔记发送 `like` 事件。 | `ts` 在 5s 内随机分布，不生成 `enter_item`。 |
| **D1 秒退** | 正常 `leave_item` 生成时 15% 概率 | 模拟用户误点或快速划过。 | `duration_sec` 限制在 `[0.2, 1.2]` 秒。 |
| **E1 超速滑动** | 正常 `leave_item` 生成时 5% 概率 | 模拟“看都不看”的极速划过。 | `duration_sec` < 0.8s 且 `content_len` > 2000。 |
| **C 极长驻留** | 正常 `leave_item` 生成时 0.5% 概率 | 模拟挂机或深度阅读。 | `duration_sec` 限制在 `[1800, 3600]` 秒。 |
| **B1 乱序数据** | 任意事件生成时 10% 概率 | 模拟网络延迟导致的延迟上报。 | `ts` 设为 `current_time - random(30, 90)` 秒。 |

## **八、 脚本运行规格 (Execution Specs)**

### **1. 流速控制 (Traffic Shaping)**
- **常规模式**：30-50 EPS (Events Per Second)，模拟社区日常平稳流量。
- **洪峰模式**：每 10 分钟自动触发一次，持续 30s，流速提升至 150-200 EPS，用于测试下游系统的背压 (Backpressure) 处理能力。

### **2. 时间机制 (Clock & Latency)**
- **事件时间 (ts)**：严格取当前系统毫秒时间戳。
- **传输延迟**：消息推入 Kafka 前随机注入 5-20ms 的物理延迟，配合 10% 的乱序注入，全方位还原真实的流处理环境。

### **3. 数据规模预期**
- 运行 1 小时预计产生约 15-20 万条行为事件，可有效覆盖 DWS 层 1min/5min/1h 的各类窗口聚合计算。
