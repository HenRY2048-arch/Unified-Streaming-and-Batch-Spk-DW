## 0.5 谁该算什么：数仓与下游的边界（回答"是否抢功"）

**一句话结论**：数仓只做"**客观、可复现、可对账的描述**"；"**为什么**"和"**该怎么办**"留给下游（看板解读、agent、推荐、运营）。

### 判定标准（两条就问完）

| 问题 | 是 → 数仓做 | 否 → 下游做 |
|---|---|---|
| 这个结果**只依赖数据本身**、换个人算也一样吗？ | ✅ 计数、比率、分布、按维度切分 | ❌ 个性化匹配度、排序分、推荐决策 |
| 它回答的是"**发生了什么**"还是"**该怎么做 / 为什么**"？ | "发生了什么" | "该怎么做""为什么会这样" |

### 以"分发漏斗"为例：它在不在职责内

漏斗做的是四件事：**数曝光、数点击、数消费、数互动**，再逐级相除。四步全是"数出来的"，没有一步在猜测原因：

- 它告诉你"**在哪一级衰减**"，不告诉你"**为什么衰减**"；
- 它按渠道/类目/位置**拆开**给你看，但不给"应该给谁多推"的建议；
- 它的分母固定是曝光，口径写死在字典里，任何人复算都一样。

所以**漏斗本身不越界**。真正越界的是"解读"：把"消费率低"直接说成"内容差"，或据此自动给内容降权——那是分析/决策，不是数仓。

### 什么才算"抢了下游的活"（我们会刻意避开）

| 越界形态 | 为什么属于下游 |
|---|---|
| 输出"这个用户会不会点"的预测分、内容-用户匹配度 | 这是模型/排序，属推荐系统 |
| 输出"该不该给这条内容加量"的策略或阈值 | 这是决策 |
| 输出"渠道 A 比 B 好，建议加预算"的因果结论 | 需要实验/因果方法，不是描述统计 |
| 每个用户一套口径的个性化看板 | 口径必须全局唯一，否则无法对账 |
| 秒级自动调参（根据热度自动改分发比例） | 这是线上决策回路 |

### 我们确实踩在线上的两处（已用纪律约束）

1. **热度是一个"打分"**（F-07）。它之所以仍在职责内，是因为：只看内容侧、与用户无关；权重写在配置里、可复现；并且明确"它不是排序分，不给谁看由下游决定"。
2. **转化率很容易被当成原因**（F-06）。数仓只提供"分解 + 对照"（按渠道/类目拆、和注入基线比），把"为什么"留给分析。

### 三条防止滑向应用层的纪律

- **只输出计数与比率**，不输出分数、不输出建议；
- **归因只做"来源记录 + last-touch"**，不做多触达/因果（见 V-01 的答复）；
- **字典带"性质"列**（业务/风控/验收/自检），避免把自检类指标当业务结论。

## 1. 宏观链路：一条事件是怎么变成指标的

### 1.1 全景：七个阶段

把整个数仓想成**一家店的账房**，七个阶段分别是：

```
①「产生」模拟器按"会话旅途"产生事件：打开 App → 看一批推送 → 点开 → 停留 → 点赞 → 关注
        ↓
②「传输」事件进消息队列（Kafka）：可能重复送达（至少一次），顺序基本有序
        ↓
③「留存证据」流式作业把每条消息解析成结构化记录，原样存下来 —— 这是**证据层**
        ↓
④「整理明细」批作业把证据整理成"一次动作一行" —— 这是**明细层**
        ↓
⑤「聚合主题」按业务问题聚合成"某天某内容/某天某作者/某天某渠道" —— 这是**主题层**
        ↓
⑥「登记语义」把每个指标"是什么、怎么算"登记成元数据 —— 这是**语义层**
        ↓
⑦「自我对账」用生成器的"标准答案"与流侧近似，检查我们算得对不对 —— 这是**对账**
```

> **真相层是旁路**：`content_groundtruth → ods/groundtruth → ⑦`；它不参与 ③–⑥ 的指标计算，
> 只用于 V-01 归因对账（否则等于抄答案）。

**每一层只做一件事**，这是刻意的：

| 阶段 | 只负责 | 不做的事（留给下一层） |
|---|---|---|
| ③ 证据层 | 把消息变成记录、按天摆好 | 不拆分推送列表、不去重、不补维表 |
| ④ 明细层 | 去重、拆分、配对、补维表 | 不聚合、不算比率 |
| ⑤ 主题层 | 按维度聚合、算比率 | 不解释口径（那是语义层的事） |
| ⑥ 语义层 | 登记口径 | 不算数 |
| ⑦ 对账 | 比较"我们算的"和"标准答案" | 不修数（修数靠重跑） |

为什么值得分这么细？因为**改动只影响一层**：换归因算法不动证据层；加一个指标不动明细层；
判"是我们的算法错还是数据错"靠对账层。这就是"可迭代"的物理基础。

### 1.2 一条事件的旅程（以"用户点开一条内容"为例）

| 阶段 | 发生了什么（人话） | 产出了什么 | 最容易丢/错的地方 |
|---|---|---|---|
| 产生 | 用户从"推荐"里点开第 3 个位置的内容，带着"哪一批推送、什么渠道、第几位" | 一条"点击"事件 | 来源字段没带上 → 后面无法归因 |
| 传输 | 事件进队列 | 消息 | 至少一次 → 会重复；重放 → 会重复 |
| 证据层 | 解析成记录，按天分区，**原样**保存 | 一条原始点击记录 | 解析丢字段；不去重（重复会带进下一层） |
| 明细层 | 去掉重复事件；把"进入"与"离开"配成一段消费；补上作者与类目 | 一条消费明细 | 没配到"离开"的点击会被算点击、但不算消费 |
| 主题层 | 按天/内容/作者/渠道聚合，算比率 | 看板上的数字 | 分母取错（最常见） |
| 语义层 | 登记"这个指标叫什么、分子分母是什么" | 指标字典 | 字典与代码不一致 |
| 对账 | 拿标准答案比对 | 命中率 | 把"对账失败"当成"业务下滑" |

### 1.3 为什么分"流"和"批"（这里决定了很多指标的形态）

- **批是账本**：每天把账重新算一遍，能重算、能对账、能回溯。绝大多数指标都在批侧。
- **流是"此刻的估算"**：只服务三类真需要秒级的东西——内容热度、作弊判定、在线人数。
- 流的结论**不是真值**：Redis 里的值过期就没了，页面读不到就回源重算；
  流侧与批侧的差，用"热度对账"来盯。

> **Tier0 不是一个 Kafka 消费者，也不是一张表**：它是流②作业，输入只读 `ods/events`；
> 输出三件事——F-07 热度（`tier0/heat_snapshot` + Redis）、Q-01 作弊（`tier0/cheat_events`）、
> U-04 在线（Redis `crt:online`）。当前每个微批重算最近 24h，不是状态化增量。

这就是为什么：

- 热度有"两个版本"（流侧秒级、批侧真值），而 CTR、留存这些只有批侧；
- 批侧可以随便重跑，流侧不可以随便清状态（清了会丢秒级服务能力，但不影响真值）。

### 1.4 指标从哪来：一张"来源地图"

| 指标族 | 它依赖哪一层 | 聚合到哪一级 | 代表问题 |
|---|---|---|---|
| 曝光与漏斗（F） | 明细层的"曝光"与"点击" | 小时 × 渠道 × 类目 | 推得准不准 |
| 消费质量（C） | 明细层的"消费片段"（进入+离开配对） | 天 × 内容 | 看得认不认真 |
| 互动（I） | 明细层的"互动动作" | 天 × 内容 | 有没有激发行动 |
| 关系与归因（R） | 明细层的"关注/取关" + 标准答案 | 天 × 作者 × 渠道 | 关系从哪来 |
| 创作侧（A） | 上面几族的作者视角 | 天 × 作者 | 我的作品表现如何 |
| 会话（S） | 明细层的"会话"（一次打开到退出） | 天 | 一次访问走多深 |
| 用户（U） | 会话 + 用户维表 | 天 | 来多少人、回不回来 |
| 质量风控（Q） | 明细层的"消费片段" + 注入规则 | 天 × 类目/作者 | 数据/内容是否异常 |
| 自我验证（V） | 标准答案 + 流侧快照 | 天（×类型） | 我们算得对不对 |

### 1.5 一次批跑的顺序，以及"哪步坏了会脏到哪"

```
维表（人/内容/关注关系）
   ↓  维表坏了 → 后面所有"按作者、按类目"的维度都会错位
明细（曝光/消费/互动/关系/发布/会话）
   ↓  明细坏了 → 主题层全错，而且错得很隐蔽（比率仍能算出来）
主题（漏斗/渠道/内容/作者/关系/会话/用户/质量/位置/留存/冷启动）
   ↓  主题层坏了 → 看板数字错，但对账不一定报（对账看的是归因）
语义字典（40 个指标的口径说明）
   ↓  字典坏了 → 看板数字对，但会被解释错（agent 尤其致命）
对账（归因命中率、热度偏差）
   ↓  对账不过 → 先别清理旧文件（否则现场没了）
维护（回收旧版本文件）
```

**一句话记住影响面**：维表错 → 维度错；明细错 → 数字错；字典错 → 解释错；对账不过 → 别动现场。

## 3. 逐个指标

> 每个指标六段：**它算什么 → 举个例子 → 怎么算出来 → 这个数能信吗 → 能拿它做什么 → Gate 建议**。
> 公式一律写成文字；字段名见附录 A。

### 3.1 F 族：曝光与漏斗

#### F-01 曝光量

- **它算什么**：系统把内容"摆到用户面前"了多少次。注意：一次推送里通常有 8 个位置，**每个位置都算一次曝光**。
- **举个例子**：某小时推荐渠道推了 125 批，每批 8 个位置 → **1,000 次曝光**。
- **怎么算出来**：先把当天所有"推送"收集起来；再把每一批里的位置列表**逐个展开**（一批 8 个就变 8 条）；
  最后按你要看的维度（哪一小时、哪个渠道、哪个类目）分组数条数。
- **这个数能信吗**：能，它是精确计数，没有估算。但它代表"摆出来"而不是"被看见"——
  用户根本没滑到也算，所以不能把它当"注意力"。
- **能拿它做什么**：一切比率的分母；判断某天某渠道的供给量。
  **别拿它做什么**：不要说"曝光 100 万所以有 100 万人看过"。
- **Gate 建议**：**硬门禁**。展开后的总条数，必须等于每一批位置数之和；三个数（推送记录、展开后的曝光、主题层曝光汇总）两两相等，
  不相等就说明"展开"这一步丢数了。

#### F-02 曝光 UV

- **它算什么**：这批曝光**碰到了多少个不同的人**。
- **举个例子**：一小时 1,000 次曝光、800 个不同用户 → 平均每人被推了 1.25 次。
- **怎么算出来**：在同一个分组里，把用户**去重**后数人头（同一个用户出现 10 次只算 1 个）。
- **这个数能信吗**：能。注意它是按账号去重，一个人换设备仍算一个。
- **能拿它做什么**：和曝光量一起判断"广度 vs 深度"——曝光多而 UV 少，说明在反复投喂同一批人。
  **别拿它做什么**：不要拿 UV 当"活跃人数"（那要看会话）。
- **Gate 建议**：软检查（UV 不可能大于曝光量）。

#### F-03 点击量

- **它算什么**：用户**主动点进去**的次数。
- **举个例子**：某小时 120 次点击。
- **怎么算出来**：直接数"点击"这类事件。注意：有些点击后来没有"离开"事件（用户切走了），
  它们**仍然算点击**——所以不要用"配对成功的消费段"来数点击，会少算。
- **这个数能信吗**：能，精确计数。
- **能拿它做什么**：点击率分子、漏斗第二级。
  **别拿它做什么**：不要把"点击"当"消费"（点了立刻退出也是点击）。
- **Gate 建议**：硬检查——点击总量必须等于"点击事件"条数（重复事件要去重后再比）。

#### F-04 点击率（CTR）

- **它算什么**：推给 100 次，有几次被点。
- **举个例子**：1,000 次曝光、120 次点击 → **12%**。
- **怎么算出来**：把**同一组**的点击数，除以曝光数。
  如果这一组没有曝光（分母是 0），结果**留空，而不是写 0**——写 0 会被误读成"真的没人点"。
- **这个数能信吗**：只要分子分母都取对，它就是精确的。
  两种常见错法：拿"点击"当分母（算出来的是"点了之后进入了多少"，完全不同的意思）；
  曝光漏掉了某些渠道（点击率会虚高，甚至超过 100%）。
- **能拿它做什么**：判断分发准不准；按渠道/位置/内容下钻。
  **别拿它做什么**：不要横向比较不同位置的点击率（排得越前天然越高）。
- **Gate 建议**：**最适合硬门禁的指标**。断言两条：结果永远在 0 到 1 之间；
  "把各分组加总后再相除"与"主题层给出的整体值"必须一致（两处独立算，对不上就是聚合写错了）。
- **疑惑**：你在算的时候去重了吗？同一个用户对同一篇内容可以多次浏览（即多次点击，准确而言是先点 击再离开然后又点击又离开往复多次）
- **答复**：这里要区分**两种完全不同的"去重"**：
  1. **事件级去重（防重复投递）**：会做。消息队列是"至少一次"，加上重放，同一条事件可能来两次；
     明细层按事件的唯一编号去重，保证"一次真实点击不会被算两次"。
  2. **业务级去重（是否把同一个人的多次行为合并）**：**不做**。点击是可重复行为——
     同一个人对同一条内容"点开→离开→再点开→再离开"三次，就是**三次点击、三段消费**。
     我们的消费配对规则是"每次离开，往前找最近一次进入"，所以多轮来回会配成多段，不会被合并。
  真正按"人"去重的地方只有三处，而且都是口径要求的：曝光 UV（按人去重）、互动的人数口径（按"人-内容"去重）、
  新增用户（按人去重）。点击率用的分子分母都**不按人合并**。

#### F-05 渠道效率

- **它算什么**：关注流、推荐、探索……哪个渠道更能把内容推给"愿意点的人"。
- **举个例子**：某小时推荐占 60% 的曝光、点击率 9%；关注流占 25% 的曝光、点击率 18%。
- **怎么算出来**：把曝光、点击、关注分别按渠道分组，再算三个比例：该渠道曝光占比、该渠道点击率、该渠道关注转化率。
- **这个数能信吗**：数字本身精确，但**渠道占比是分发策略动态调整出来的**。
  今天推荐占比变高，会让整体点击率变化——这是策略变了，不是渠道变差。
- **能拿它做什么**：看"渠道结构"和"渠道效率"两张图；判断"是不是某个渠道被砍了/被灌了"。
  **别拿它做什么**：不要跨天直接比同一渠道的点击率（用户群和策略都可能在变）。
- **Gate 建议**：软检查（各渠道曝光占比加起来接近 100%）。
- **疑惑**：你分成哪些渠道了？按照什么标准分的？
- **答复**：渠道不是我们事后划分的，而是**生成器在分发时打上的标签**，固定六个值：
  关注流、推荐、探索、个人主页、列表、话题。分发控制器每个批次挑一个渠道——按"用户成熟度 + 渠道近期反馈"
  动态调权重，基线是推荐 45%、关注流 35%、探索 20%；候选池为空时会回落到探索。
  一批曝光只有一个渠道；点击与互动事件本身不带渠道，是通过"批次编号"继承那一批的渠道；
  关注事件自带渠道（可能是"从主页关注"）。所以看板上的"渠道"就是这六个值，
  "无来源"只出现在关注类事件里（用户不是从内容页关注的）。

#### F-06 分发漏斗

- **它算什么**：从"看到"到"点开"到"看完"到"互动"，**哪一级掉得最狠**。
- **举个例子**：1,000 曝光 → 120 点击（12%）→ 100 段消费（10%）→ 30 次互动（3%）。
- **怎么算出来**：四级各自按同一组维度数出来，再相邻两级相除。
- **这个数能信吗**：能。但要注意"消费"这一级需要"进入+离开"配对成功；
  没配上的点击会表现为"点了但没消费"——这可能是真实情况（用户切走了），也可能是数据问题。
- **能拿它做什么**：定位问题层级（是分发不准，还是内容不吸引人）。
  **别拿它做什么**：不要用"互动次数除以曝光"去说明"有多少人互动"（那是人次，不是人数）。
- **Gate 建议**：软检查——三个比率都在 0 到 1 之间；点击率 ≥ 消费率（通常成立）。

#### F-07 内容热度

- **它算什么**：这条内容"此刻有多烫"。它**只跟内容有关，跟用户无关**——不是"你喜欢什么"。
- **举个例子**：某内容一小时里 100 次曝光、20 次点击、5 个赞、3 个收藏、2 条评论、1 次转发，
  另有 10 段消费共停留 300 秒（每段最多算 30 秒）。给曝光每次记 0.1 分，点击 1 分，赞 3 分，
  藏 4 分，评 6 分，转 8 分，停留每 50 秒记 1 分。于是：
  曝光 10 分 + 点击 20 分 + 赞 15 分 + 藏 12 分 + 评 12 分 + 转 8 分 + 停留 6 分 = **83 分**。
- **怎么算出来**：每隔几秒做一次结算——先把最近 1 小时、最近 24 小时两段分别圈出来；
  在两段里各数六类动作；每类乘一个"重要程度"（转发最重、曝光最轻）；停留按秒折分、单段封顶 30 秒；最后相加。
  所有内容都会留一份快照（供对账），前 200 名写进缓存（供页面秒级读取）。
- **这个数能信吗**：它是**定义出来的分数**，不是物理量；权重一改就不可比。
  流侧是秒级估算，批侧重算才是真值。
- **口径限制**：**停留分不要求窗口内有曝光**。所以有些内容可能“曝光 0、仅凭停留上榜”，
  长驻留注入会放大这个现象；这不是计算 bug，字典会把该限制写进 `limitations`。
- **能拿它做什么**：热榜、实时排序、推荐信号（概念上）。
  **别拿它做什么**：不要拿它当"内容质量"的绝对值；不要跨权重版本比较。
- **Gate 建议**：只能做结构化检查——快照非空；同一时刻"1 小时的条目数"不应超过"24 小时的条目数"。

#### F-08 位置偏差 / 排序质量

- **它算什么**：排在前面的内容点击率高，是"位置好"还是"内容好"。
- **举个例子**：第 0 位点击率 18%，第 7 位 4%——这就是典型的位置红利。
- **怎么算出来**：按"渠道 + 位置"分组，分别数曝光、点击数，再算每个位置的点击率，顺带算该位置的平均排序分。
- **这个数能信吗**：能，但"位置"和"内容质量"是混在一起的；排序分本身是模拟器的排序函数输出，不是线上真实分。
- **能拿它做什么**：判断排序是否合理；验证"位置字段有没有接错"。
  **别拿它做什么**：不要用排序分去做"模型评估"。
- **Gate 建议**：软检查——首位点击率通常高于末位；若完全反向，多半是位置字段接反了。
- **疑惑**：你怎么知道内容排序？排序是属于内容本身的元数据还是某个字段？
- **答复**：**内容本身没有"全局排名"**。排序是**每次曝光自带的上下文**——那一批推送里它排第几（位置），
  以及当时算出的排序分。同一条内容，对不同用户、不同批次，位置和分数都可能不同。
  所以这里分析的是"**位置与点击的关系**"（位置红利），不是"内容的排名"。
  排序分是生成器**分发那一刻**算出来的（新鲜度、兴趣匹配、作者影响力、噪声加权），
  它是"这一次分发的决策痕迹"，不是内容元数据。
  放到真实生产：位置来自推荐系统的排序结果，排序分往往不落库（要专门埋）；我们的表结构里预留了它，
  但**没有它也能算位置偏差**——位置本身就是字段。

### 3.2 C 族：消费质量

#### C-01 平均停留

- **它算什么**：一段消费平均看多久。
- **举个例子**：某内容当天有 20 段消费，合计 800 秒 → 平均 **40 秒**。
- **怎么算出来**：先把"进入"和"离开"配成一对（同一会话、同一条内容，离开时往前找最近那次进入）；
  再取"离开"事件里记录的停留时长；最后求平均。中位数可按需现算（当前未落表），它更抗异常。
- **这个数能信吗**：能。停留时长是模拟器按"内容长度 ÷ 阅读速度"采样出来的，是模型真值；
  时间戳相减只用来交叉验证（我们实测两者差的中位数是 3 毫秒）。
- **能拿它做什么**：内容吸引力的代理指标；和负反馈率一起看最有用。
  **别拿它做什么**：不要单独用平均停留判断"内容好"——长驻留注入会把均值拉得很离谱。
- **Gate 建议**：可以做硬检查——"停留时长"与"进入/离开时间差"的中位数应该接近 0（证明时间链自洽）。
- **追加建议**：不认为需要做硬Gate，这只能检查生成器的时间逻辑问题，生成器本质上只是项目因没有真实数据源而做的妥协，而非生产真相
- **答复**：同意，这条我按你的意见**下调定位**了：它不是业务门禁，而是**模拟器自洽检查**。
  在生产里"停留"本来就是墙钟时间，不存在"两条时间线"的问题；它只验证我们自己的假数据源是否自洽。
  因此它属于新体系里的 **FX（夹具自检）类**，处置为 **G4 观察**，或者放进"生成器变更后的回归"，
  **不作为每日批链路的阻断门**。§7 已经把 FX 类单独列出来，和 DR/IV/CV/QL/RC 区分开。

#### C-02 完读率（推断，不是观测）

- **它算什么**：这么长的内容，用户大概读完了多少。
- **举个例子**：内容 3,000 字，按每秒 77.5 字算，预计要读 38.7 秒；实际停留 20 秒 → 大约 **52%**。
- **怎么算出来**：用实际停留时间除以"预计阅读时间"（内容长度除以平均阅读速度），
  结果超过 3 倍的按 3 倍算（防止长驻留把比例拉爆）。
- **这个数能信吗**：**不能当事实**。数据源没有"读完"这个事件，这只是一个推算。
  长内容扫读会被判"没读完"，短内容几乎都"读完"。
- **能拿它做什么**：看分布、比较长短内容的消费差异。
  **别拿它做什么**：不要用它考核内容质量，也不要设硬阈值。
- **Gate 建议**：不建议做门禁。

#### C-03 负反馈率

- **它算什么**：多少比例的曝光让用户"不满意"。
- **举个例子**：1,000 次曝光里，200 次秒退、10 次点踩 → 约 **21%**。
- **怎么算出来**：数两件事——秒退（0.2 到 1.2 秒就走）和点踩；两项加起来除以曝光数。
  “不到 0.8 秒且长内容”的超速是 Q-02 的诊断量，**不再重复加到 C-03**，否则会与秒退重叠。
- **这个数能信吗**：部分能。**秒退总量约 20% 是模拟器注入的**（D1/E1 区间重叠，不能拆成 15%+5%），不是真实不满；
  判断"内容真的不行"，要把这部分基线减掉。
- **能拿它做什么**：内容质量预警。
  **别拿它做什么**：不要把它当成"用户真实情绪"的绝对值。
- **Gate 建议**：软检查（0 到 1 之间）；真正适合做门禁的是"注入率是否接近预期"（见 Q-02）。

### 3.3 I 族：互动

> 先记住一条规则，否则这族一定看不懂：
> **点赞、点踩、收藏是"一次性"的**（同一个人对同一条内容只会发生一次，且赞与踩互斥）；
> **评论、转发是"可重复"的**。所以：点赞数 = 点赞人数，而评论数 ≠ 评论人数。

#### I-01 互动量

- **它算什么**：发生了多少次互动，以及**多少人真的表过态**。
- **举个例子**：某内容有 10 个人点赞、2 个人各评论了 3 条。
  按"人次"算：10 + 6 = **16 次**；按"人数口径"算：10 个点赞的人 + 2 个评论的人 = **12 对（人-内容）**。
- **怎么算出来**：先按动作类型分别计数（这是"人次"）；
  再把"谁对哪条内容"去重后计数（这是"人数口径"）。因为点赞是一次性的，所以点赞的人次天然等于人数。
- **这个数能信吗**：能，精确。注意"人数口径"是"发生过任何互动的用户-内容对"，不分动作类型。
- **能拿它做什么**：内容的整体活跃度；互动率的分子。
  **别拿它做什么**：不要把两个口径混着用，否则会推出"互动率大于 100%"。
- **Gate 建议**：硬检查——人数口径不可能大于人次口径。

#### I-02 互动率

- **它算什么**：看到内容的人里，多大比例动手了。
- **举个例子**：800 个不同用户看到（曝光 UV 800），10 个赞、2 个评论 →
  人数口径 12 ÷ 800 = **1.5%**；人次口径 16 ÷ 1,000 次曝光 = **1.6%**。
- **怎么算出来**：一次性行为（赞/藏/踩）用"人数 ÷ 曝光 UV"；
  可重复行为（评论/转发）用"人次 ÷ 曝光次数"。
- **这个数能信吗**：精确，但两种分母**不能混**：同一个人被推 10 次也只可能赞 1 次，
  用"曝光次数"当分母会系统性低估。
- **能拿它做什么**：衡量内容激发行动的能力。
  **别拿它做什么**：不要和"点击率"混为一谈（分母不同）。
- **Gate 建议**：软检查（0 到 1 之间）。

#### I-03 点击→互动转化率

- **它算什么**：点进来的人里，有多少后来还是互动了。
- **举个例子**：当天 120 次点击、16 次互动 → 约 **13%**。
- **怎么算出来**：同一天、同一条内容的互动人次除以点击数。
- **这个数能信吗**：是"日级"转化，不是"每次点击"的转化：一个人点 3 次、赞 1 次，会被算成"3 次点击产生 1 次互动"。
- **能拿它做什么**：看"点进来值不值"。
  **别拿它做什么**：不要用它对单次点击做因果判断。
- **Gate 建议**：软检查。

#### I-04 收藏率

- **它算什么**：多少人把内容"存起来以后用"——这是比点赞更强的意图信号。
- **举个例子**：800 个用户看到，24 次收藏 → **3%**。
- **怎么算出来**：收藏数除以曝光 UV（因为收藏也是一次性的，用人数口径）。
- **这个数能信吗**：精确。注意"点踩过"的内容不允许收藏，所以那类内容收藏率为 0 是设计，不是异常。
- **能拿它做什么**：判断内容的"长尾价值"。
- **Gate 建议**：软检查（0 到 1）。

#### I-05 私信量

- **它算什么**：从公开互动走向私聊的次数。
- **怎么算出来**：数"私信"事件。
- **这个数能信吗**：精确，但私信优先发给"关注的人"，所以它和关注量强相关。
- **能拿它做什么**：关系强度的一个信号（弱保留）。
- **Gate 建议**：软检查（非负，且与关注量同向）。

### 3.4 R 族：关系与归因

#### R-01 粉丝来源构成

- **它算什么**：今天涨的粉，分别来自哪条内容、哪个渠道。
- **举个例子**：某作者某天在推荐渠道涨了 30 个粉，其中 12 个来自内容 A。
- **怎么算出来**：先把"关注"按"作者 + 渠道"分组计数；再按"作者 + 渠道 + 来源内容"计数，
  取数量最大的那条内容作为"最大来源"。
- **这个数能信吗**：精确。但有些关注没有来源（用户是从主页关注的），会归到"无来源"。
- **能拿它做什么**：创作者中心"粉丝从哪来"；判断内容对涨粉的贡献。
  **别拿它做什么**：不要把"无来源"当成数据错误。
- **Gate 建议**：硬检查——各来源加总应等于关注事件总数。

#### R-02 关注转化率

- **它算什么**：看到（或点开）内容的人里，多少最后关注了作者。
- **举个例子**：1,000 曝光、120 点击、30 个关注 → 按曝光算 **3%**，按点击算 **25%**。
- **怎么算出来**：关注数分别除以曝光数、点击数，两个口径都保留。
- **这个数能信吗**：精确。两个口径差别很大，**不要互相比较**：曝光口径天然低。
- **能拿它做什么**：衡量分发到关系沉淀的效率。
  **别拿它做什么**：不要拿"曝光口径"去和别人的"点击口径"比。
- **Gate 建议**：软检查（0 到 1）。

#### R-03 关注转化途径（last-touch）

- **它算什么**：这次关注，**最后一下**是被哪条内容、哪个渠道打动的。
- **举个例子**：某次关注来自内容 A、推荐渠道、第 3 位。
- **怎么算出来**：直接取关注事件自带的"来源内容、来源用户、渠道"；
  再拿这些信息和生成器的标准答案比对（就是 V-01）。
- **这个数能信吗**：只能代表"最后一次触达"的功劳，不代表整条路径的贡献分配。
- **能拿它做什么**：回答"内容→关注"的转化路径。
  **别拿它做什么**：不要用它做多触达归因的结论（我们没做 Markov/Shapley）。
- **Gate 建议**：用 V-01 的命中率做门禁（≥99%）。

#### R-04 取关率 / 净涨粉

- **它算什么**：今天涨了多少、掉了多少、净赚多少。
- **举个例子**：某作者新增 8 个关注、1 个取关 → 净增 **7**。
- **怎么算出来**：关注数减取关数。
  另外还给一个"当天结束仍有效的粉丝总数"——这是从关注关系表按时间有效性数出来的**存量**，不是累加值。
- **这个数能信吗**：精确。存量与净增不一定相等（取关会改变历史），这不是错误。
- **能拿它做什么**：创作者中心的核心指标。
- **Gate 建议**：**硬检查**——逐行满足"净增 = 新增 − 取关"；汇总等于明细层的关注/取关事件数。

#### R-05 粉丝活跃度

- **它算什么**：涨来的粉，是活人还是"僵尸粉"。
- **举个例子**：某天新增 20 个粉丝，其中 6 人在 7 天内与该作者的内容互动过 → **30%**。
- **怎么算出来**：取当天新增的"谁关注了谁"；再看这些人在"关注之后的 7 天内"有没有和该作者的内容互动；算比例。
- **这个数能信吗**：能，但**最近 7 天的新粉还没观察满**，比率会偏低（右截断）。
- **能拿它做什么**：判断增长质量。
  **别拿它做什么**：不要把最近几天的低值当作"粉丝不活跃"的结论。
- **Gate 建议**：只做趋势观察。

#### R-06 进主页量

- **它算什么**：多少人点进了作者主页（关注路径上的中间一步）。
- **怎么算出来**：数"进主页"事件。
- **这个数能信吗**：精确，但它不是关注。
- **Gate 建议**：软检查（不超过当日点击量）。

### 3.5 A 族：创作侧

> 这一族是"作者视角"：同样的曝光/点击/涨粉，换个分组维度而已。

#### A-01 作者曝光 / 点击 / 互动

- **它算什么**：我发的作品一共被推了多少次、被点了多少次、被互动了多少次。
- **举个例子**：某作者某天：曝光 3,000、点击 360、互动 40 → 点击率 12%。
- **怎么算出来**：把曝光、点击、互动分别按"作者"分组汇总；点击率是同一作者的点击除以曝光。
- **这个数能信吗**：能，和 F 族是同一批数据，只是换了分组。
- **能拿它做什么**：创作者中心的主面板。
  **别拿它做什么**：不要用它代替"粉丝增长"（那是 R/A-02）。
- **Gate 建议**：硬检查——全站各作者的曝光加总必须等于总曝光。

#### A-02 作者涨粉 / 掉粉

- **它算什么**：我的内容给我带来多少新粉、掉了多少。
- **举个例子**：新增 8、掉 1 → 净 7，累计粉丝 1,205。
- **怎么算出来**：关注按"被关注的人"分组计数；取关同理；净增是两者之差；
  "累计粉丝"是按"当天结束时这段关注关系仍然有效"数出来的存量。
- **这个数能信吗**：精确。存量与净增不一致是正常的（取关会改变历史）。
- **能拿它做什么**：创作者增长看板。
- **Gate 建议**：硬检查"净增 = 新增 − 掉粉"。

#### A-03 作者产出

- **它算什么**：今天发了几条内容。
- **怎么算出来**：数"发布内容"事件，按作者分组。
- **这个数能信吗**：精确。
- **能拿它做什么**：判断"投入"；和涨粉一起看"投入产出比"。
  **别拿它做什么**：产出多不等于效果好。
- **Gate 建议**：硬检查——各作者发布数加总等于发布事件数。
- **疑惑**：在生成器的加速时钟里面，作者发布内容一般遵循怎样的概率算法？
- **答复**：现在的规则是——**生成器每"推进一步"，有 1% 的概率触发一次发布**（配置里叫发布速率，默认 0.01），
  见 `RealTime` 的 `MockGenerator`。触发后随机挑一个创作者（约 15% 的用户是创作者），
  生成一条新内容：长度 50–5000 字符，类目取该作者的主类目（没有就随机），标签 1–3 个，
  发布时间取该作者的**事件时钟**（所以跟随加速时钟走），内容编号递增。
  **要注意的是**：这个 1% 是"**每步**"而不是"**每事件天**"，所以在加速/降速时，
  "每位作者每天发几条"会随每秒步数变化，不是一个稳定的业务参数。
  如果你要"每作者每天 N 条"这种可控语义，需要把它改成按事件时间速率来算——这属于生成器改动，
  我建议放到 Gate/编排之后单独做（会动生成器，但不改契约）。

#### A-04 内容冷启动

- **它算什么**：新内容发出去的第一天，系统给没给它机会。
- **举个例子**：内容 A 发布后 24 小时内被曝光 500 次、点击 45 次 → 点击率 9%。
- **怎么算出来**：以"发布时间"为起点，取之后 24 小时内这条内容的曝光、点击、互动，分别计数后相除。
- **这个数能信吗**：能，但**发布不满 24 小时的条目是"半程成绩"**，不能和满 24 小时的比。
- **能拿它做什么**：判断分发对新内容是否公平；创作者关心"我的新作品能不能起来"。
- **Gate 建议**：只看趋势（比如"新内容 24 小时零曝光的比例"），不卡具体数值。

### 3.6 S 族：会话

> 会话＝一次"打开 App 到退出"；模拟器里一次会话最多 12 步、每步看一批 8 个候选。

#### S-01 会话数

- **它算什么**：今天被打开了几次（**不是人数**）。
- **举个例子**：一天 5,000 次会话、3,000 个用户 → 平均每人 1.7 次。
- **怎么算出来**：把同一会话的记录归到一起，按天数"有多少个会话"。
- **这个数能信吗**：精确。
- **能拿它做什么**：访问量；和 DAU 一起看"人均打开次数"。
- **Gate 建议**：硬检查——主题层的会话数必须等于明细层的会话条数。

#### S-02 会话时长

- **它算什么**：每次打开平均待多久。
- **举个例子**：一次会话从 10:00 打开到 10:06 结束 → 6 分钟。
- **怎么算出来**：用会话结束时间减开始时间（事件时间轴），再求平均。
  另有一个"内容停留之和"：只算真的在看内容的时间，不含在列表里滑来滑去。
- **这个数能信吗**：能。但长驻留注入会把均值拉高，看中位数更稳。
- **能拿它做什么**：访问深度。
  **别拿它做什么**：不要把"会话时长"和"平均停留"混为一谈（后者是单条内容）。
- **Gate 建议**：软检查（非负；突然翻倍要查长驻留）。

#### S-03 会话长度分布

- **它算什么**：用户一次打开会做几步事——多数人做几步、少数人做很多步。
- **怎么算出来**：数每个会话里的事件条数，看它的分布（中位数、长尾）。
- **这个数能信吗**：能；但会话上限是 12 步，所以"很长"最多到 12。
- **能拿它做什么**：判断产品是"快进快出"还是"深度浏览"。
- **Gate 建议**：软检查（事件条数在 1 到 12 之间）。

#### S-04 每会话曝光 / 点击 / 消费 / 转化

- **它算什么**：一次打开里，走了漏斗的哪几步。
- **举个例子**：一次会话曝光 32 次（4 批 × 8 个位置）、点开 5 条、完整消费 4 条、互动 2 次。
- **怎么算出来**：把会话内的记录按类型分别计数；曝光要按"位置"展开后计数（不是按批次数）。
- **这个数能信吗**：能。
- **能拿它做什么**：分析"一次访问能挖多深"。
- **Gate 建议**：硬检查——会话里的曝光加总必须等于总曝光。

#### S-05 会话跳出

- **它算什么**：打开后只看了一眼就走。
- **怎么算出来**：数"只曝光了 1 次"的会话，除以会话总数。
- **这个数能信吗**：能，但在当前模拟器里这个值几乎恒为 0——
  因为每步至少推 8 个位置，会话天然很难只曝光 1 次。**它现在没有区分度**。
- **能拿它做什么**：暂时只能做边界检查。
- **Gate 建议**：不建议单独设门禁。

### 3.7 U 族：用户

#### U-01 DAU

- **它算什么**：今天有多少人**真的用了**（有会话才算）。
- **举个例子**：3,000 个不同用户今天有会话 → DAU 3,000。
- **怎么算出来**：把今天的会话按用户去重后数人头。
- **这个数能信吗**：能。注意它比"有任意事件就算活跃"的老口径更严格。
- **能拿它做什么**：用户大盘。
- **Gate 建议**：硬检查——DAU 必须等于会话表里的去重用户数；为 0 说明当天没数据。

#### U-02 新增用户（两个口径 + 缺口）

- **它算什么**：今天新来了多少人；以及我们的"注册事件"有没有漏。
- **举个例子**：10 月 18 日，注册事件算出 23 人，但"第一次出现"算出 30 人 → 缺口 −7。
- **怎么算出来**：
  1. 注册口径：数今天"注册时间"落在今天的人；
  2. 观测口径：数今天"第一次出现在任何事件里"、且不是种子用户的人；
  3. 缺口：注册数减观测数。
- **这个数能信吗**：两个口径各自精确，但**缺口可以为负**：
  种子用户没有注册事件，却会在第一天"第一次出现"——那 7 个人就是这种情况。
- **能拿它做什么**：判断埋点是否完整；监控"缺口突然变大/变小"。
  **别拿它做什么**：不要要求缺口必须为 0 或必须为正。
- **Gate 建议**：硬门禁可以卡"缺口相对历史区间的突变"（比如突然 −500），而不是卡绝对值。

#### U-03 留存 / 回访

- **它算什么**：今天来的人，明天还来吗、七天后还来吗。
- **举个例子**：某天注册的 20 人里，有 5 人在次日还有会话 → 次日留存 **25%**。
- **怎么算出来**：注册用户用**注册日**做 cohort，种子用户用**首见日**做 cohort，并用 `cohort_type` 区分；
  再看 cohort 里的每个人，在"cohort 日 + 1/3/7 天"是否还有会话；有会话的人数除以 cohort 人数。
  U-03 的主口径只看 `cohort_type=registered`；seed 行保留，但只用于“存量回访”观察。
- **这个数能信吗**：能，但要注意三件事：
  ① 档位是 1/3/7；14 天等数据跨度足够再加；
  ② 最近 7 天的 cohort 还没观察满，`is_mature=false`，7 日留存会是 0；
  ③ 种子用户不是“新增”，不能混进 U-03 主口径。
- **能拿它做什么**：判断粘性；判断某次改动后用户是否更容易流失。
  **别拿它做什么**：不要用最近几天的 7 日留存下结论。
- **Gate 建议**：硬检查"留存率在 0 到 1 之间"；"cohort 人数突然变少"要报警（上游丢人）。

#### U-04 在线活跃（秒级）

- **它算什么**：此刻大约有多少人在线。
- **举个例子**：最近 15 分钟有 20 个不同用户产生过事件 → 在线 20。
- **怎么算出来**：Tier0 每隔几秒取"最近 15 分钟有事件"的用户去重计数，写进 Redis（TTL 900s）。
- **这个数能信吗**：是"最近一段时间的近似"，不是精确在线；缓存过期后读不到不代表没人。
- **能拿它做什么**：秒级页面上的"在线人数"。
- **Gate 建议**：只做"缓存里有值"的软检查。

### 3.8 Q 族：质量与风控

#### Q-01 作弊判定

- **它算什么**：有没有人在刷评论、刷赞。
- **举个例子**：某个用户 5 秒内给 15 条不同内容点赞 → 判定 A2。
- **怎么算出来**：流式作业每批扫最近 24 小时：
  ① 同一用户对同一条内容 60 秒内评论 5 条以上 → A1；
  ② 同一用户 5 秒内点赞 15 次以上且涉及 10 条以上不同内容 → A2。
  判定结果落库（含用户、内容、时间窗、次数），可审计。
- **这个数能信吗**：规则命中是精确的；但**轨迹是追加上去的**，同一判定可能被多个批次各写一次，
  统计"作弊用户数"时要按"规则 + 用户 + 内容 + 时间窗"去重。
- **能拿它做什么**：风控信号；验证"注入能不能被检出"。
- **Gate 建议**：可做"注入一次至少检出一次"的召回检查。

#### Q-02 秒退 / 短停留 / 长内容短停留 / 极长驻留

- **它算什么**：多少比例的用户"点开就关"、"滑得太快"、"挂着不走"。
- **举个例子**：1,000 段消费里，200 段是 0.2–1.2 秒的秒退、140 段是 <0.8 秒短停留 → 20% / 14%。
- **怎么算出来**：在消费明细上分别计数，再统一除以同一分组的 `consume_cnt`：
  ① 停留 0.2–1.2 秒（秒退，可观测基线 20%）；② 停留 <0.8 秒（短停留，可观测基线 14%）；
  ③ 停留 <0.8 秒且 `content_len > 2000`（长内容短停留，仅诊断）；④ 停留 30–60 分钟（长驻留，基线 0.5%）。
- **这个数能信吗**：能，但要注意 ② 与 ③ 是**包含关系**，不能相加；D1（0.2–1.2s）与 E1（<0.8s）也重叠，
  所以 15%/5% 只能作为生成器参数，不能分别观测。QL 用总量 20%/14%/0.5% 作基线；
  ③ 只用于解释“长内容被秒划”的业务现象。
- **能拿它做什么**：**最适合做质量门**：比例明显偏离预期，说明生成器配置变了、或者链路丢/重了数据。
- **Gate 建议**：QL-1-01 用 20%/14%/0.5% 可观测基线，±3pp 告警、±5pp 或连续 2 天同向偏离降级；
  单日消费样本 <200 时改用 7 日滚动，避免小样本误报。

#### Q-03 异常分布

- **它算什么**：异常集中在哪些类目、哪些作者。
- **怎么算出来**：把上面四类异常按"类目 + 作者"拆开。
- **这个数能信吗**：能；作者粒度行数会很多，做图先按类目上卷。
- **Gate 建议**：硬检查（各类目/作者的异常数加总等于总数）。

### 3.9 V 族：自我验证（不是业务指标）

#### V-01 归因对账一致率

- **它算什么**：我们算出来的"这次关注/互动是被哪条内容带来的"，和生成器的标准答案对得上吗。
- **举个例子**：某天 like 208 次，命中 208 次 → **100%**。
- **怎么算出来**：从标准答案出发，左连接我们的互动/关注明细：
  ① 精确率＝“连上且渠道与来源内容都一致”÷“连上的”；
  ② 召回率＝“连上的”÷“标准答案总数”；
  ③ `missing_cnt` 单列，记录标准答案里有、数仓没找到的转化。
- **这个数能信吗**：能，这是最硬的证据（用的是生成器的真值）。
  注意一个陷阱：交互类事件的"渠道"要靠它所属的推送批次反查——这一步坏了会出现"只有关注类 100%"的假象。
- **能拿它做什么**：证明归因口径有效；判断改动是否破坏了归因。
- **Gate 建议**：硬门禁——精确率 ≥ 99% 且 `missing_cnt=0`（或召回 ≥ 99.9%）；最近实测 100%。
- **疑惑**：理论上我们不做归因，因此该项目的归因是否应拆成两种维度/程度？
- **答复**：先澄清"不做归因"的准确含义——我们不做的是**多触达归因与因果归因**
  （Markov、Shapley、增量实验），也就是不回答"这次转化里每个触达各占多少功劳"。
  我们做的是两层，且只有两层：
  1. **证据层**：事件自带"从哪来"（来源内容、来源用户、渠道）——这是**事实记录**，不是判断；
  2. **口径层**：last-touch（只取最后一次触达）——这是**一条明确的规则**，写进字典。
  所以"要不要拆成两种维度/程度"——建议拆成两个**轴**，而不是两个新指标：
  - **时间窗**：当前是"会话级"（一次打开内），未来可选"归因窗口"（如 7 天）；
  - **分配规则**：当前是"最后一次"，未来可选"第一次/线性"。
  这两个轴都在**口径层**加组合，证据层完全不用动——这正是分层的意义。
  另外，V-01 对账的只是"**我们的来源记录是否与真值一致**"，与"用哪种分配规则"无关：
  真值里记的也是同一批来源字段。所以扩不扩归因规则，都不影响 V-01 的通过标准。

#### V-02 热度对账

- **它算什么**：流侧算出的热度，和批侧按同一口径重算的结果差多少。
- **怎么算出来**：从热度快照里取每个"时刻 × 内容 × 窗口"最新的一条；
  用**同一个时刻**当时间锚点，从证据层按同一套评分规则重算；两数相减、相除。
- **这个数能信吗**：**现在恒为 0**，因为流侧与批侧用的是同一份公式、同一个时刻。
  它目前的作用是"回归检查"：一旦不为 0，说明代码或口径被改歪了。
- **能拿它做什么**：等流侧改成"增量维护"（只记近似计数）之后，它才会变成真正的"近似误差"。
- **Gate 建议**：现在只做"必须为 0（或极小）"的回归检查，不设误差阈值。

## 4. 常见误解（FAQ）

**问：为什么曝光量是"推送条数"的 8 倍？**
答：一次推送里有 8 个位置，**每个位置都算一次曝光**。这不是重复计数——用户确实在屏幕上拥有了 8 个"被看到的机会"。

**问：为什么点赞数可以直接当"点赞人数"？**
答：模拟器规定点赞是**一次性**的：同一个人对同一条内容只会赞一次，且赞与踩互斥。所以"次数"和"人数"相等。
但评论可以重复，所以评论数不等于评论人数。

**问：为什么留存会显示 0？**
答：三种可能：① 你看的是"7 日留存"，而数据只跑到第 3 天（还没观察满）；② 那天确实是 0；
③ cohort 取错了（registered 应用注册日，seed 才用首见日）。

**问：为什么热度榜上会有"曝光 0"的内容？**
答：热度公式里"停留"是独立加分项。一条内容如果被长时间消费（甚至是被注入的长驻留），
即使窗口内没有曝光，也能拿到分。这是目前的口径选择，不是计算错误。

**问：为什么不能拿两个渠道的点击率直接比？**
答：渠道占比是动态调整的，用户群也不同（关注流的人更"熟"）。跨渠道比点击率，等于把"渠道质量"和"用户结构"混在一起。

**问：为什么新增用户的"缺口"是负数？**
答：种子用户（系统初始化时就存在的 1000 人）没有注册事件，但他们第一次出现会被算进"观测口径"。
所以"注册 − 观测"可以是负的；它衡量的是"注册事件覆盖不到的首次出现"。

**问：为什么热度对账永远是 0？**
答：流侧和批侧用的是**同一份公式、同一个时刻**，所以必然相等。它现在是"定义一致性"检查；
等流侧改成增量维护，才会产生真正的近似误差。

**问：同一个人多次点开同一条内容，会被去重吗？**
答：**点击不会被合并**——点三次就是三次点击、三段消费（每次离开都配对它前面最近的一次进入）。
会按人去重的只有三处：曝光 UV、互动的人数口径、新增用户。
另外有一层"事件级去重"（按事件唯一编号），那是防重复投递，不是业务合并。

**问：渠道是哪几种？谁决定的？**
答：六个值——关注流、推荐、探索、个人主页、列表、话题；由**生成器在分发时决定**（权重随用户成熟度与渠道反馈动态变化，
基线推荐 45% / 关注流 35% / 探索 20%）。点击与互动的渠道通过"批次编号"继承自那一批曝光；
关注事件自带渠道。"无来源"只出现在关注类事件里。

| 你看到的现象 | 最可能出问题的层 | 先看什么 | 常见原因 |
|---|---|---|---|
| 某天数字全是 0 | 证据层/明细层 | 那天有没有原始事件；明细表有没有行 | 上游没送、日期取错（时区） |
| 曝光量比预期多很多 | 证据层 | 是否有重复事件（重放/消费位点回退） | 去重没生效 |
| 点击率大于 100% | 主题层 | 曝光是否被过滤（分母漏了） | 分组键不全、join 丢行 |
| 点击多、消费少得离谱 | 明细层 | "进入/离开"是否配对成功 | 会话被切碎、离开事件缺失 |
| 作者/类目大面积空白 | 维表层 | 维表是否重建成功、内容是否在维表里 | 维表没跑、内容晚于维表 |
| 互动率大于 1 | 主题层 | 分子分母是否用了不同口径 | 人次/人数混用 |
| 留存整列为 0 | 主题层 | `day_offset` 与数据最大日期 | 窗口未满（正常） |
| 粉丝活跃度最近几天很低 | 主题层 | 7 天窗口是否已满 | 右截断（正常） |
| 作弊表行数暴涨 | 流层 | 是否重复写入同一判定 | 跨批重复（需去重） |
| 归因命中率突然下降 | 明细层 | 交互类的渠道是否为空 | 渠道回填坏了 |
| 热度榜前几名很怪 | 流层 | 是否是长驻留注入、权重是否被改过 | 口径问题，不是 bug |

## 7. Gate 的分级体系（为什么"硬/软"不够用）

> **权威版本已抽为独立文档：[`Gate_Grading_Scheme.md`](./Gate_Grading_Scheme.md)**
> （含 20 条注册表、清单字段、Airflow 映射、Gate v1 定值与 agent 可调边界）。
> 本节保留摘要，便于阅读连贯；**阈值、等待策略、降级开关以独立文档为准**。

"硬/软"只回答了**失败之后怎么办**这一个维度。真正决定一条 gate 该不该存在、该不该阻断的，是三件独立的事：

> **查什么（类别） × 查到多深（层级） × 失败怎么办（处置）**，
> 再挂两个属性：**作用范围**（分区/表/跨表）与**责任方**（流/批/对账/生成器）。

### 7.1 处置等级（Action）：G0–G4

| 级别 | 名字 | 含义 | 调度器表现 | 下游怎么处理 |
|---|---|---|---|---|
| **G0** | 阻断 | 数据不可信，立即停 | 退出码 1 | 下游不跑；**保留现场**（不做清理） |
| **G1** | 等待 | 上游还没到，等一等 | 退出码 2，按间隔重试，超时升级为 G0 | 下游等待 |
| **G2** | 降级继续 | 有瑕疵但可用 | 退出码 0 + 清单打 `untrusted/partial` | 下游继续，但看板标"未定稿" |
| **G3** | 告警 | 不影响正确性，值得注意 | 退出码 0 + 通知 | 正常跑 |
| **G4** | 观察 | 只记录，不干预 | 退出码 0 | 正常跑 |

**规则**：**处置等级由"这条检查能不能被判定"决定，而不是凭感觉。** 算术恒等 → 允许 G0；
统计量（注入率、留存）→ 默认只能 G3；推断量（完读率）→ 只能 G4。

### 7.2 检查类别（Class）：六类，各有自己的"层级阶梯"

| 类别 | 查什么（人话） | 层级阶梯（由浅到深） | 默认处置 |
|---|---|---|---|
| **DR 就绪** | 数据到没到、够不够 | L1 分区存在 → L2 非空 → L3 水位/时效 → L4 量级与去重后一致 | L1–L2：G0；L3：G1；L4：G2 |
| **IV 守恒** | 同一件事的两种数法是否相等 | L1 单表算术 → L2 跨表汇总 → L3 跨天累计 | G0 |
| **CV 口径** | 口径本身有没有自相矛盾 | L1 边界（0–1）→ L2 结构（人次≥人数、净增=新增−取关）→ L3 字典与代码一致 | G0 |
| **QL 质量** | 分布是否偏离"正常" | L1 固定基线（注入率）→ L2 滚动基线（近 7 天中位）→ L3 分布形态 | L1：G3（偏离大升级 G2）；L2–L3：G3 |
| **RC 对账** | 与"标准答案"是否一致 | L1 抽样 → L2 全量 | G0（低于阈值）或 G3（轻微偏差） |
| **FX 夹具自检** | 模拟器自身是否自洽 | L1 时间自洽 → L2 注入率 → L3 契约完整性 | **G4**（变更后回归时才升为 G0） |

> **FX（夹具自检）为什么单列**：像"停留时长与时间戳是否一致""秒退是否约 20%"这类检查，
> 验证的是**模拟器这个"假数据源"的逻辑**，不是"生产数据质量"。生产里停留本来就是墙钟，
> 不存在这个问题；把它们混进业务门禁，会让"门禁通过/失败"失去业务含义。
> 它们应该跑在**生成器变更后的回归**里，而不是每天卡在批链路前面。

### 7.3 组合规则（不是自由搭配）

1. **一条 gate 的完整定义** ＝ 类别 + 层级 + 处置 + 作用范围 + 责任方 + 阈值来源。
2. **只有 IV / CV 允许 G0**：它们可判定、无统计噪声，错了就是代码或数据错了。
3. **DR 允许 G0/G1**：到没到是事实；但"等多久"是策略。
4. **QL / FX 默认不允许 G0**：统计量有波动，卡死只会制造误报。
5. **同一类检查在不同层级可以有不同处置**（例如 DR 的 L2 阻断、L4 降级）——这就是"分级"的意义。

### 7.4 我们链路的 Gate 注册表（Gate v1）

编号规则：`类别-层级-序号`。作用范围：`分区 / 表 / 跨表 / 跨链路`。

| 编号 | 类别 | 检查（人话） | 处置 | 范围 | 何时跑 |
|---|---|---|---|---|---|
| `DR-1-01` | 就绪 | 目标日期有分区 | G0 | 分区 | 每天批跑前 |
| `DR-2-01` | 就绪 | 该日期事件数 > 0 | G0 | 分区 | 批跑前 |
| `DR-3-01` | 就绪 | 最大事件时间越过该日水位 | 当前日 G1；历史日缺水位 G2 | 分区 | 批跑前 |
| `DR-4-01` | 就绪 | 当天事件量在近 7 天中位的 0.5×~2× 内 | G2 | 分区 | 批跑前 |
| `DR-4-02` | 就绪 | 去重后事件数 ≥ 去重前 × 期望比例 | G2 | 表 | 证据层落完后 |
| `IV-1-01` | 守恒 | 展开后的曝光条数 = 各批位置数之和 | G0 | 表 | 明细层后 |
| `IV-2-01` | 守恒 | 主题层曝光/点击/消费/互动加总 = 明细层条数（点击须去重或读 `dwd/click`） | G0 | 跨表 | 主题层后 |

| `RC-2-02` | 对账 | V-02 偏差 ≤1e-9（当前口径）；无快照记 G3 limitation | G3 | 跨链路 | 对账后 |

| `FX-3-01` | 夹具 | 契约字段齐全、枚举值合法 | G4（回归时 G0） | 表 | 生成器回归 |

### 7.5 与调度器的对应关系

| 处置 | 退出码 | Airflow 里怎么配 |
|---|---|---|
| G0 阻断 | `1` | 任务失败 → 下游节点不执行 |
| G1 等待 | `2`（一次性检查）／`0` 或 `1`（`--wait` 模式） | **Gate 内部等待/重试**；Airflow 只看最终 0/1 |
| G1h 等人批 | `2` + `needs_confirmation` | Airflow 暂停/人工恢复，不自动重试 |
| G2 降级 | `0` + `pass_with_limitations` + `publish_final=false` | 正常继续；下游读 `partition_status` 决定是否发布 |
| G3 告警 | `0` + 通知 | 正常继续；告警任务单独挂 |
| G4 观察 | `0` + 写清单 | 正常继续 |

**清单（manifest）最小字段**：`run_id, stage, gate_id, class, level, dt, status, metric_value, threshold, action_taken, approval, publish_final, policy_version, contract_hash, input_fingerprint, ts, detail`。
它同时是"跳过已完成段"和"事后追责"的依据。

### 7.6 Gate v1 已冻结

**v1 已定（2026-10-20 冻结）**：

- G0–G4 五级处置、六类检查、`类别-层级-序号` 的编号规则；
- IV/CV 才允许 G0；QL/FX 默认只告警/观察；
- FX 类（模拟器自洽）**不进每日阻断链路**，只做变更回归。

**已冻结的取值**：

1. `QL`：20%/14%/0.5% 可观测基线；±3pp 告警；±5pp 或连续 2 天同向偏离降级；单日消费 <200 用 7 日滚动。
2. `DR-3`：5 分钟 × 3 次（15 分钟），开发 1 分钟 × 3；超时 G0。
3. `G2`：仅 QL/DR-4 启用，`pass_with_limitations` 且 `publish_final=false`；IV/CV/RC 不降级。
4. `V-02`：当前 `rel_diff ≤1e-9`；未来 `p95 ≤1%`、`max ≤5%`；无快照记 G3 limitation，不阻断批侧。
5. `QL-2`：cohort 规模相对 7 日中位 ≤30% 告警、>50% 降级；渠道占比绝对变化 ≤5pp 告警、>10pp 降级。
