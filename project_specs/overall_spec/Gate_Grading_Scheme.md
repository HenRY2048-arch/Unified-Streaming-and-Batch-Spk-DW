# Gate 分级方案（Gate Grading Scheme）

> **这份文档解决什么**：编排里的"门禁"不能只有"硬/软"两档。本文定义**怎么分类、怎么分层、
> 失败后怎么处置**，并给出一份可落地的注册表。
>
> **不解决什么**：长期阈值调优。v1 的阈值、等待时长、降级开关已冻结（见 §5/§8）；
> 后续由 agent 在给定区间内调参，但不能改口径与断言内容。
>
> 版本：v3.1（2026-10-20）｜上游依据：`Metric_Implementation_Guide.md`、`Warehouse_Design.md`
>
> v2 变更：引入**"证据结论 × 处置动作 × 审批级别"三层**（参考 HSADL 的 evidence gate 后与本方案合并）；
> 增加**双产物**（人看的 md + 机器读的 json）与**分区信任标记**；新增 §14「data agent 的读契约（预留）」。
>
> v3 变更：**冻结 Gate v1 的四项处置取值**（QL 容差 / DR-3 等待 / G2 范围 / V-02 门槛）；
> V-01 改为**精确率 + 召回率**双检查；明确 Q-01 去重键、Q-02 拆分与分母；
> 增加 §5.1「P3.8 前置实现条件」；清单与 `partition_status` 落 Delta；调度器定为 **Airflow**。
>
> v3.1 运行校准：DR-3 历史日缺水位→G2；QL-1 基线改 20%/14%/0.5%（D1/E1 重叠）；V-02 无快照→G3 limitation。

## 0. 为什么"硬/软"不够

"硬门禁 / 软检查"只回答了一个问题：**失败之后怎么办**。但一条门禁要落地，至少还要回答：

1. **查什么**（数据到没到？算术对不对？分布偏没偏？）；
2. **查到多深**（表在不在 → 有没有行 → 够不够新 → 量级对不对 → 去重后一致否）；
3. **谁来担责**（流侧、批侧、对账、还是生成器自身）；
4. **下游怎么处理**（停、等、继续但打标、只告警）。

所以本文用**三个维度**定义一条 gate：**类别 × 层级 × 处置**，再挂两个属性：**作用范围**、**责任方**。

## 0.5 两轴模型总览（v2：结论 ≠ 处置）

**为什么要拆开**：同一条检查，在不同的消费方眼里，"结论"和"该做什么"不是一回事。
看板可以"带限制继续"，结算必须"停"，agent 可能"只读但标注不可信"。
如果门禁直接输出"阻断/告警"，消费方就失去了自己决定怎么用的空间。

于是拆成三层：

### 轴一：证据结论（Status）——这条数据"算不算够"

| Status | 含义 | 谁会觉得它够 |
|---|---|---|
| `pass` | 在声明的口径下没发现实质问题 | 所有消费方 |
| `pass_with_limitations` | 有已知限制，但不推翻当前用途 | 看板/探索可用；结算/对外需谨慎 |
| `needs_confirmation` | 有一个"需要人点头"的具体动作（改数据/花钱/改口径） | **必须先拿到审批**，否则不继续 |
| `blocked` | 口径/守恒/对账等**硬错误**，当前用途不成立 | 谁都不能用 |

### 轴二：处置动作（Action）——运行器"接下来做什么"

| Action | 含义 |
|---|---|
| `G0` | 阻断：下游不跑，保留现场 |
| `G1` | 等上游：按间隔重试，超时升级 G0 |
| `G1h` | **等人批**：停下来等一个具体动作的批准（不是自动重试） |
| `G2` | 降级：继续，但打 `degraded` 标记 |
| `G3` | 告警：继续 + 通知 |
| `G4` | 观察：只记录 |

### 第三层：审批级别（Approval）——"这个动作要不要人批"

| 级别 | 适用 | 例子 |
|---|---|---|
| `safe_auto` | 只读、幂等、无破坏性 | 跑检查、重算某天分区、重跑对账 |
| `needs_approval(action_id)` | **改数据 / 花钱 / 改变语义** | `VACUUM`、跨天补数、跳过某段、修改阈值 |

### 默认映射（可由策略覆盖）

| 证据结论 | 默认动作 | 审批 |
|---|---|---|
| `pass` | `G4` | safe_auto |
| `pass_with_limitations` | `G2`（或 `G3`） | safe_auto |
| `needs_confirmation` | `G1h` | needs_approval |
| `blocked` | `G0` | —（不需要批，直接停） |
| （上游未到） | `G1` | safe_auto |

> 一句话：**Status 回答"能不能用"，Action 回答"现在做什么"，Approval 回答"谁说了算"。**
> 三者分开，才可能让同一份数据同时服务看板（可降级）、结算（必须阻断）与 agent（只读带标注）。

## 1. 维度一：处置等级（Action，G0–G4）

| 级别 | 名字 | 什么情况下用 | 调度器表现 | 下游怎么处理 |
|---|---|---|---|---|
| **G0** | 阻断 | 结果可判定、错了就是错（算术/口径/对账） | 退出码 `1`，任务失败 | 下游不跑；**保留现场**，不做清理 |
| **G1** | 等待 | 不是错，只是上游还没到 | 退出码 `2`，按间隔重试 | 下游等待；超时升级为 G0 |
| **G2** | 降级继续 | 有瑕疵但可用于"先看"，不能用于结算 | 退出码 `0` + 清单标记 `degraded` | 继续跑，但看板/下游读清单后标"未定稿" |
| **G3** | 告警 | 不影响正确性，但值得人看一眼 | 退出码 `0` + 通知 | 正常跑 |
| **G4** | 观察 | 只记录，不做任何干预 | 退出码 `0` + 清单 | 正常跑 |

**核心规则**：**处置等级由"可判定性"决定，不由心情决定。**

- 算术恒等、口径自洽 → 允许 G0；
- 统计量（注入率、留存、渠道占比）→ 默认最高 G3；
- 推断量（完读率）与"模拟器自洽"（FX）→ 默认 G4。

## 2. 维度二：检查类别（Class）与层级（Level）

| 类别 | 查什么（人话） | 层级阶梯（由浅到深） | 默认处置 |
|---|---|---|---|
| **DR 就绪** | 数据到没到、够不够 | L1 分区存在 → L2 非空 → L3 水位/时效 → L4 量级与去重后一致 | L1/L2 G0；L3 G1；L4 G2 |
| **IV 守恒** | 同一件事两种数法是否相等 | L1 单表算术 → L2 跨表汇总 → L3 跨天累计 | G0 |
| **CV 口径** | 口径本身有没有自相矛盾 | L1 边界（0–1）→ L2 结构（人次≥人数、净增=新增−取关）→ L3 字典与代码一致 | G0 |
| **QL 质量** | 分布是否偏离"正常" | L1 固定基线（注入率）→ L2 滚动基线（近 7 天中位）→ L3 分布形态 | L1 G3（大偏离升 G2）；L2/L3 G3 |
| **RC 对账** | 与"标准答案"是否一致 | L1 抽样 → L2 全量 | G0（低于下限）或 G3（轻微偏差） |
| **FX 夹具自检** | **模拟器自身**是否自洽 | L1 时间自洽 → L2 注入率 → L3 契约完整性 | **G4**（生成器变更后的回归才升 G0） |

> **FX 为什么单列**：像"停留时长与时间戳是否一致""秒退是否约 20%"这类检查，验证的是**假数据源**的逻辑，
> 不是生产数据质量。生产里停留本来就是墙钟，不存在这个问题。把 FX 混进每日门禁，会让"门禁通过/失败"失去业务含义。

## 3. 维度三：作用范围与责任方

| 属性 | 取值 | 说明 |
|---|---|---|
| 作用范围 | 分区 / 表 / 跨表 / 跨链路 | 决定 gate 的粒度，也决定失败时影响谁 |
| 责任方 | 流侧 / 批侧 / 对账 / **生成器（FX）** | 出问题先找谁；FX 的责任方永远是生成器 |

## 4. 组合规则（硬约束，不允许自由搭配）

1. **一条 gate 的完整定义** ＝ 类别 + 层级 + 处置 + 作用范围 + 责任方 + 阈值来源。
2. **只有 IV / CV 允许 G0**：它们可判定、无统计噪声，错就是错。
3. **DR 允许 G0/G1**：到没到是事实，"等多久"是策略。
4. **QL / FX 默认不允许 G0**：统计量有波动，卡死只会制造误报。
5. **同一类检查在不同层级可以有不同处置**（如 DR 的 L2 阻断、L4 降级）——这就是"分级"的意义。
6. **FX 不进每日阻断链路**：只在生成器变更时作为回归门。

### 5.1 P3.8 前置实现条件（已落地）

以下不是"建议"，而是 Gate v1 能按本表落地的前提：

1. **点击证据链**：默认补 `dwd/click`（一行一次 `enter_item`，带渠道/内容维）；若时间紧，可临时用
   `ods/events where event_type='enter_item'` 的 `dropDuplicates("event_id")`，但必须在 Gate 中显式声明；不能继续用未去重的 ODS 点击。
2. **V-01 精确率/召回率**：`verify/attribution` 增加 `missing_cnt` 与 `recall`；truth 左连接 warehouse，
   `total_cnt` 必须来自 truth，而不是 `inner join` 后的行数。
3. **Q-02 分母与拆分**：`dws/quality_daily` 增加 `consume_cnt`、`short_stay_cnt`、`long_content_short_stay_cnt`；
   `short_stay` 对 14% 可观测基线，`long_content_short_stay` 只作诊断，不参与 QL-1-01 的基线断言。
4. **Q-01 去重键**：统计口径固定为 `rule + user_id + item_id + window_start`；表内允许跨批重复 append，
   但不允许 Gate/agent 直接 `count(*)`。
5. **R-06**：`enter_profile` 纳入 `dwd/relation`（不改契约，只改过滤枚举）。
6. **字典限制**：`semantic/metric_dict` 增加 `limitations` 列，至少覆盖 C-02 推断量、C-03 含注入噪声、
   R-05/A-04 右截断、V-01/V-02 自检性质。
7. **留存与重跑口径**：U-03 cohort 改为注册日/首见日 + `cohort_type`；`user_daily` 的 reg/obs 在写
   `replaceWhere` 前先过滤到窗口内，避免谓词外行导致约束失败。

## 6. 清单（manifest）与"按段跳过"

每条 gate 执行后写一行清单，字段最小集：

| 字段 | 用途 |
|---|---|
| `run_id` / `stage` / `gate_id` | 谁、哪一段、哪条门 |
| `class` / `level` | 类别与层级（便于统计"哪类门最常响"） |
| `dt` | 作用日期（分区级门要带） |
| `status` | `pass / pass_with_limitations / needs_confirmation / blocked / wait` |
| `metric_value` / `threshold` | 实际值 vs 门槛（可追溯） |
| `action_taken` | 实际处置（G0/G1/G1h/G2/G3/G4） |
| `approval` | `safe_auto` 或 `needs_approval:<action_id>` |
| `publish_final` | 是否允许下游把该分区当"定稿"使用（G2 时必须为 `false`） |
| `policy_version` | 当时用的策略版本（agent 调参后可回溯） |
| `contract_hash` / `input_fingerprint` | 口径与输入指纹（防止"改了口径仍放行"） |
| `ts` / `detail` | 时间与原始错误信息 |

**用途**：

1. **按段跳过**：同一 `dt` + `stage` 若已 `pass` 且输入指纹未变，重跑时直接跳过；
2. **事后追责**：哪条门、哪一天、谁触发的降级，一查就有；
3. **策略演进**：agent 调阈值时，用历史 `metric_value` 分布做依据，而不是拍脑袋。

## 7. 与调度器的对应（Airflow）

| 处置 | 退出码 | 调度侧配置 |
|---|---|---|
| G0 阻断 | `1` | 任务失败 → 下游节点不执行 |
| G1 等待 | `2`（一次性检查）／`0` 或 `1`（`--wait` 模式） | **由 Gate 内部等待/重试**；Airflow 只看到最终 0/1，避免把"等上游"和"失败"混为一谈 |
| G1h 等人批 | `2` + `needs_confirmation` | Airflow 暂停/人工恢复；不在每日 DAG 里自动重试 |
| G2 降级 | `0` + `pass_with_limitations` + `publish_final=false` | 继续；下游读 `partition_status` 决定是否发布 |
| G3 告警 | `0` + 通知 | 继续；告警节点单独挂 |
| G4 观察 | `0` + 清单 | 继续 |

## 8. 扩展点：未来 agent 介入的边界

这部分是给"后续拓展"留的接口。原则：**agent 可以调"松紧"，不能改"事实"**。

| agent **可以**决定 | agent **不可以**改 |
|---|---|
| 阈值取值（在给定区间内） | 口径定义（分子/分母、去重键、窗口） |
| 等待/重试节奏 | gate 的"断言内容"（只能调阈值，不能改断言） |
| 是否启用 G2 降级 | 哪些类别允许 G0（IV/CV 才允许） |
| 告警的聚合与降噪 | 编号规则与清单字段 |
| 跳过"已完成且输入未变"的段 | FX 类的归属（必须留在生成器侧） |

**v1 定值（agent 只能在区间内调整松紧，不能改断言）**：

| 项 | v1 定值 | 可调区间（建议） | 说明 |
|---|---|---|---|
| QL 注入率容差 | 秒退 20%、短停留 14%、长驻留 0.5%；±3pp 告警；±5pp 或连续 2 天同向偏离降级 | ±1 ~ ±5 | D1/E1 重叠，15%/5% 不可分别观测；单日消费 <200 用 7 日滚动 |
| QL-2 cohort 规模 | 相对 7 日中位偏离 ≤30% 告警；>50% 降级 | 20% ~ 50% | 避免小 cohort 噪声 |
| QL-2 渠道占比 | 绝对变化 ≤5pp 告警；>10pp 降级 | 3pp ~ 10pp | 渠道占比是策略变量，不轻易阻断 |
| DR-3 等待 | 当前日 5 分钟 × 3 次；开发 1 分钟 × 3；历史日缺水位直接 G2 | 1 分钟 × 2 ~ 10 分钟 × 6 | 历史日等待没有意义，按 limitation |
| RC-2-01 归因 | 精确率 ≥0.99 且 `missing_cnt=0`（或召回 ≥0.999） | 精确率 0.95 ~ 1.00；missing 断言不可调 | 当前实测 1.00 |
| G2 降级开关 | **仅 QL/DR-4 启用**；`publish_final=false` | 开/关 | IV/CV/RC 不允许降级 |
| V-02 热度 | 当前 `rel_diff ≤1e-9`；未来 `p95 ≤1%`、`max ≤5%` | 当前 0 ~ 1e-6；未来 0.5% ~ 5% | 无快照按 DR 处理，不能 pass |
| FX 回归触发 | 生成器代码/配置变更时 | 每日/变更时 | 不进每日链路 |

## 附录 A：参考实现对照（HSADL，非规范）

> 来源：`github.com/limingrui679-design/high-stakes-analytics-decision-lab`（MIT）。
> 该仓库是"Agent Skill + Python 脚本"的形态：`SKILL.md` 是契约与工作流，`scripts/*.py` 是执行体，
> `references/data-quality-gate.md` 是门禁的完整规约。以下是**可直接借鉴**与**不应照搬**的部分。

### 12.1 它的三个关键设计

1. **门禁状态是"证据结论"，不是"处置动作"**：它只出四种状态——
   `ready` / `ready_with_documented_limitations` / `needs_user_confirmation` / `blocked`，
   由调度层决定"继续 / 带限制继续 / 停下等人批 / 不许分析"。
2. **门禁与"数据契约"绑定，且 fail-closed**：先声明用途、粒度、主键、目标与时间窗；
   源文件 SHA-256、清洗动作 ID、审批记录任一变化，门禁直接拒绝继续。
3. **两类动作**：`safe_auto`（语义无歧义、可逆：去空白、缺失哨兵归一、数值/日期规范化）
   与 **需按动作 ID 显式批准**（删行、删列、插补、截尾、合并类目、单位/时区/粒度变更）。
   审批后才生成新文件，并保留转换日志与"清洗前后"两份报告。

### 12.2 我们该借的（建议）

| 借鉴点 | 为什么对我们有价值 | 落到哪 |
|---|---|---|
| **状态与处置分离** | 我们现在的 G0–G4 其实是"处置"；缺"证据结论"这一层（如"可继续但有限制""需人工确认"） | 本文 v2：`status × action` 两轴 |
| **`needs_user_confirmation` 作为独立状态** | "等上游"与"等人批"是两件事，混成 G1 会让等待语义不清 | 新增 `G1h`（人工等待） |
| **门禁绑定契约 + fail-closed** | 我们的口径在文档里，但 gate 运行时没有"契约指纹"；改了口径/输入却仍放行是隐患 | manifest 增加 `contract_hash` / `input_fingerprint` |
| **动作 ID + 审批** | 我们的重算/VACUUM/补数/跳段都属于"改数据或花钱"的动作，应当可追溯 | `safe_auto` 与 `needs_approval` 两类动作 ID |
| **双产物（md + json）** | 人看 md、机器/agent 读 json；我们目前只有表 | 每次运行产出 `gate-report.md` + `gate-report.json` |
| **按路由给不同规则** | 描述/预测/处方三类问题的门禁规则不同；对应我们的"阶段 × 类别"策略 | 注册表按阶段细化 |

### 12.3 我们不该照搬的

- **它没有"等上游延迟"的概念**（它是单数据集分析，不是常驻管道）：我们的 `G1`（水位未到）必须保留。
- **它没有"降级"这一档**（只有"带限制继续"）：我们的 `G2` 对看板更有意义（"先发布但打未定稿"）。
- **它的粒度是"一个数据集一次分析"**：我们是"按天分区、跨表、跨链路"，需要 `DR/IV/RC` 这类管道级类别。
- **它的 128MiB / 50 万行等阈值**是它自己的夹具约束，与我们的数据量无关。

### 12.4 合并后的形态（已采纳）

```
证据结论 status：pass | pass_with_limitations | needs_confirmation | blocked
处置动作 action：G0 阻断 | G1 等上游 | G1h 等人批 | G2 降级 | G3 告警 | G4 观察
审批级别 approval：safe_auto | needs_approval(action_id)
```

映射示例：

| 证据结论 | 默认处置 | 说明 |
|---|---|---|
| `pass` | G4 / 继续 | 一切正常 |
| `pass_with_limitations` | G2 降级（或 G3） | 可用于"先看"，不用于结算 |
| `needs_confirmation` | **G1h**（等人批） | 例如要 VACUUM、要跨天补数、要改阈值 |
| `blocked` | G0 | 口径/守恒/对账失败 |
| （上游未到） | G1 | 只等数据，不等人 |

> 结论：**它补的是"证据结论 + 审批"这一层，我们已有的是"处置 + 类别 + 注册表"**；
> 两者合并才是完整的分级（v2 已按 §0.5 合并）。

## 附录 B：双产物与分区信任标记

### B.1 为什么每次运行要出两份产物

| 读者 | 读什么 | 为什么 |
|---|---|---|
| **人**（你、看板运营） | `gate-report.md` | 要的是"这次为什么放行/为什么降级/要我批什么"，一段话能看懂 |
| **机器/agent** | `gate-report.json` | 要有稳定 schema、可程序化判断，不能靠解析 Markdown |

两份**由同一份 manifest 生成**，避免"文档说通过、机器读到失败"这种漂移。

### B.2 `gate-report.json` 的稳定字段（建议）

```
run_id, generated_at, policy_version, contract_hash
stages[]                      # 每个阶段的结论与耗时
gates[]                       # 每条 gate 一行
  ├─ id / class / level       # 例如 IV-2-01 / IV / L2
  ├─ status                   # pass | pass_with_limitations | needs_confirmation | blocked
  ├─ metric_value / threshold
  ├─ action                   # G0/G1/G1h/G2/G3/G4
  └─ approval                 # safe_auto | needs_approval:<action_id>
limitations[]                 # 已知限制（人话，可直接贴给用户）
approvals_required[]          # 待批动作（id + 影响 + 建议）
artifacts[]                   # 本次产出的表/文件/报告
```

### B.3 `ops/partition_status`：把"某天能不能用"变成可查询的事实

| 列 | 说明 |
|---|---|
| `dt` / `table` | 哪一天、哪张表 |
| `status` | 该分区最终结论（同上四种） |
| `limitations` | 已知限制（如"右截断""上游缺 1 小时"） |
| `policy_version` | 用哪版策略判的（阈值改过可追溯） |
| `updated_at` | 何时更新 |

**为什么需要它**：看板和 agent 不应该每次自己去重跑门禁。它们只需要问一句
"10-18 的 `dws/content_daily` 能不能用？"——查一行就够。
这也是"降级"能被下游真正用起来的前提：**结论落在表里，而不是只留在日志里。**

## 附录 C：data agent 的读契约（预留，后置工程）

> 本文不设计 agent 本身，只回答三个问题：**它负责什么、按什么负责、怎么读我们的数据**。

### C.1 它负责什么（四件事）

1. **路由**：把用户的问题映射到指标编号（如"最近什么内容最火"→ F-07 + C-01 + I-02）；
2. **取数**：按指标字典的粒度与维度取数，**不自己发明口径**；
3. **解释**：按字典给出分子/分母、可下钻维度、已知限制（右截断、注入噪声、推断量）；
4. **标注可信度**：引用该分区的 `status`；`blocked` 拒答，`pass_with_limitations` 必须带限制，`needs_confirmation` 必须说明"待批"。

**它不负责**：改口径、改阈值、重算定义、写数仓、替人做决策。

### C.2 它按什么负责（四个依据）

| 依据 | 回答什么问题 |
|---|---|
| `semantic/metric_dict` | **有什么指标、口径是什么、能按哪些维度下钻** |
| `ops/partition_status` | **这一天这张表能不能用、有什么限制** |
| `gate-report.json` + `run_manifest` | **为什么是这个结论、哪条门给的、用的哪版策略** |
| `contract_hash` | **口径有没有变过**（变了就不能跨版本比较） |

### C.3 它怎么读我们的数据

```
只读三张表 + 一个 JSON：
  semantic/metric_dict      → 选指标、拿口径
  ops/partition_status      → 拿可信度
  ops/run_manifest          → 拿运行时间线
  gate-report.json          → 拿结论细节与待批项

需要明细时：读 dwd/*，但每次引用必须带 metric_id + dt + 表名
不直接读 ods/*：那是未解析、未去重的原始证据
```

### C.4 七条硬规则（写进 agent 的系统提示，也写进工具层）

1. **只读**：不写任何表；要改数只能提"重算请求"，由批作业执行；
2. **必须引用**：`metric_id + dt + 表名` 三件套缺一不可；
3. **`blocked` 必须拒答**，并说明是哪条门（如"曝光守恒不成立"）；
4. **`pass_with_limitations` 必须带限制**（如"7 日留存右截断，实际偏低"）；
5. **`needs_confirmation` 必须说"待批"**，不能把待批动作当成已完成；
6. **不得自行改口径/重算**：口径以字典为准，改动只能走文档与代码变更；
7. **不得把自检类指标（V-01/V-02）当业务结论**（字典 `nature` 列已标注）。

### C.5 一个问答示例（引用形态）

> 问："10 月 18 日哪条内容最火？"
>
> 答："按 F-07（内容热度，小时窗口）看，10-18 热度最高的是内容 200517。
> 依据：`semantic/metric_dict` 的 F-07 口径；分区状态 `ops/partition_status(dt=2026-10-18)` = `pass_with_limitations`，
> 限制是"热度含停留分，可能受长驻留注入影响"；运行版本 `policy_version=gate-v2`。
> 如果要做结算用途，建议改用批侧真值窗口（24h）并先看 `verify/heat`。"

### C.6 后置工程需要预留的东西

| 要预留 | 用途 |
|---|---|
| `semantic/metric_dict` 的 `nature` / `grain` / `dims` | agent 选表与解释的依据 |
| `ops/partition_status` | 一次性回答"能不能用" |
| `gate-report.json` 的稳定 schema | agent 程序化读取 |
| `policy_version` / `contract_hash` | 版本可比性与回滚 |
| `semantic/metric_dict.limitations` | 右截断、注入噪声、推断量等必须能如实转述 |
