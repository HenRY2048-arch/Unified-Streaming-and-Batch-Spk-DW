## 1. 项目定位

**一句话**：一个"微博式"内容社区行为流的**批流一体实时数仓**，其中**主角是内容分发**。

**目标产物**：让这套平台能回答两类问题——

1. **内容分发效率**：曝光 → 消费 → 互动的漏斗，按内容 / 作者 / 渠道切分；
2. **关系怎么长出来的**：粉丝来源构成、关注转化路径。

**消费者**：

- **创作者中心**（主看板）—— **批侧**，天/周尺度、要全量、可回溯；
- **推荐信号**（可选，未定）—— 若做，属**流侧**，秒/分尺度、短时效。

> 取舍原则：**不做应用层**。业务真实性由模拟数据源脚本承担，而非自建 Web 应用。

## 2. 业务模型（业务是根源）

### 2.1 社区本质

**"内容分发 + 关系沉淀"的双边社区**——其中"关系沉淀"是"内容分发"的**副产物**，不是中心叙事。

### 2.2 业务飞轮

```
作者供内容 → 系统分发（关注流 / 推荐 / 探索，比例动态变化）→ 用户消费 → 反馈 → 回流到分发与供给
```

### 2.3 三类行为（总线的三根主干）

| 主干 | 包含 | 备注 |
|---|---|---|
| 用户 ↔ 帖子 | 消费（曝光/点击/停留/退出）、互动（赞/藏/评/转） | 主链路 |
| 用户 ↔ 用户 | 关系（关注/取关）、交流（私信/转发） | 社交关系＝**被分析的对象** |
| 用户 ↔ 系统 | 登录/会话/签到 | 主要是**上下文与维度**，不必主题化 |

### 2.4 事件的"根"：曝光

**分发产生的"曝光"事件必须存在，且必须携带来源/渠道。**
没有它，一切分析只能从"点击"开始，路径在之前就已经断了。

### 2.5 作者

**作者回归**，作为内容供给侧的**归属维度**——它是一个**静态维表属性**（一次 join 即得），
**不是**跨事件归因。它支撑创作者中心的完整成立。

> 澄清：当初移除作者是**最小可行性（MVP）的范围取舍**，不是对作者/归因的否定。

## 3. 主题域（总线矩阵雏形）

| 主题域 | 过程粒度 | 归因角色 | 时效倾向 |
|---|---|---|---|
| 用户↔帖子 · 消费 | 一次曝光/一次消费（带时长、位置、来源） | **触达层**（归因候选集） | 流（实时热度）+ 批（明细分析） |
| 用户↔帖子 · 互动 | 一次动作（赞/藏/评/转，无时长） | **转化层** | 批（单实体计数交回 OLTP） |
| 用户↔用户 · 关系 | 边变更（关注/取关） | 社会图的演化 | 批（可配流做刷粉/异常） |
| 用户↔用户 · 交流 | 消息/转发事件 | 社交互动强度 | 批 |
| 用户↔系统 | 会话/登录/签到 | 上下文与平台维度 | 不必主题化 |
| （横切）风控/异常 | 序列状态机 | 质量与安全 | 流 |

**组织原则**：**主题域同时是"归因分治"和"批流分级"的边界**——每个主题自己定义归因口径、自己选时效。

## 4. 架构：批流一体

### 4.1 定义

在本项目（Spark 生态，无 Flink）中，**批流一体 = 以批为真值、以流为近似；两者共用一套存储 + 一套逻辑定义**。

### 4.2 一致性契约（核心难点，也是价值所在）

- **两种一致性模型**：流给"早期可见的近似"，批给"最终正确"；迟到数据被 watermark 丢掉后，**由批补回**——批是流的正确性兜底。
- **同一份逻辑、两种实现**：流侧是带 watermark 的增量，批侧是全量窗口；**流侧实际是批侧的近似子集**（会话类流侧做不准，只能靠批）。
- **同一张表、两个写入者**：流持续追加，批必须能**幂等重写已写分区**（Delta `replaceWhere`/`MERGE`），并明确"谁覆盖谁、何时结算"。
- **两套调度模型**：流常驻、批触发；调度器已定 **Airflow**（`LocalExecutor + Postgres`，2026-10-20）。
- **必须约束**：批作业要能**按窗口重跑**（因归因窗口 + 迟到数据）。

### 4.3 存储

统一落在 **Delta**（湖仓），表层为 ODS / DWD / DWS / DIM。
另设**真相层** `ods/groundtruth`：由独立 topic `content_groundtruth` 接入，只用于 V-01 归因对账，
**不参与指标计算**（否则等于抄答案）。

## 5. 分层与分级

### 5.1 分层

| 层 | 职责 |
|---|---|
| ODS | 贴源解析（JSON → 结构化） |
| DWD | 明细 + 维度补全（含作者、标签、来源） |
| DIM | 用户 / 帖子 / 作者 / 标签 / 时间 / 渠道 |
| DWS | **按主题域**的聚合与归因产物 |
| 服务层 | 创作者中心（读持久表）；实时热度（Redis 缓存） |

### 5.2 分级（新鲜度）——**推翻"纯准实时"**

| 级别 | 谁要 | 时效 | 落在哪 |
|---|---|---|---|
| 单实体计数（帖的赞/藏/评论数、用户粉丝数） | 页面直显 | 即时 | **OLTP 直查，不进数仓** |
| 反作弊、限流信号 | 风控 | 秒级 | **流** |
| 帖/话题实时热度、热榜 | 产品 | 秒–分 | **流**（Redis 缓存） |
| 曝光/点击/互动的日级与窗口聚合 | 报表 | 小时–天 | **批** |
| 消费质量、会话/路径、创作者中心 | 运营/创作者 | 天–周 | **批** |

> 原则：**Redis 是持久聚合表的缓存/投影，不是真值**——TTL 到期＝回源重刷，不是数据丢失。

## 6. 归因框架

### 6.1 分层

- **证据层（只有一份，统一）**：事件 + 会话 + **来源**。不带任何归因口径，因此换算法不需返工。
- **口径层（分而治之）**：一条归因 = **转化事件 × 候选触达集 × 归因窗口 × 分配规则**。按问题单点定义，**只物化要服务的那些**，避免预炸宽表。

### 6.2 分配规则谱系

- 启发式：last-touch / first-touch / linear / time-decay / position（U 型）；
- 数据驱动：Markov 链"移除效应"、Shapley 值；
- 因果：增量实验（incrementality / A-B）。

### 6.3 旅程归因（已定）

- **刻度：会话级 + 归因窗口**（不做终身旅程）；
- **位置：批侧**（全量、有序、可重算，且对性能友好）；
- 路线类型有限（如内容转化、关注转化），不建议"万物皆旅程"。

### 6.4 本项目的独特优势

**模拟器掌握 ground truth**——分发路径由生成器决定，因此可用真值**校验**归因口径（last-touch / Markov / Shapley 孰近），这在真实环境几乎做不到。
