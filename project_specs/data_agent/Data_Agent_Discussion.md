## 2. 用户提出的核心痛点

### 2.1 批流计算结果不一致

项目采用“批为真值、流为近似”的架构，用户最担心的是：

- 批侧与流侧结果发生对账差异；
- Agent 不能只报告“有差异”，还要帮助判断差异的性质；
- 需要区分真实计算错误、时间边界差异、重复事件、覆盖不足、流侧近似和口径变化。

### 2.2 凌晨批作业失败后的信息断层

典型场景：

1. 批作业在每日凌晨运行；
2. 作业失败；
3. 第二天只看到失败结果，不知道具体发生了什么；
4. 需要人工逐项查日志、对表、判断影响范围；
5. 缺少可继续追踪的排查路径和解决思路参考。

尤其需要关注：任务可能在 Gate 之前失败，此时当天的 Gate 报告和完整分区信任状态可能尚不存在。

### 2.3 讨论中补充的痛点

| 痛点 | 说明 |
|---|---|
| 失败类型不清 | “失败”可能来自中间件、Airflow、Spark、上游没数据、空分区、计算错误、Gate 阻断等 |
| 缺少统一事故现场 | 成功运行有门禁产物，但失败任务可能没有完整结果可供 Agent 分析 |
| 对账差异容易被过度解释 | `diff != 0` 不等于链路计算错误，也不等于同一个根因 |
| 静默错误更危险 | 任务成功但数据为空、分布突变或不可信时，仍可能被下游直接使用 |
| 缺少事故时间线 | 需要知道上次正常时间、当前差异起点、输入/代码/口径是否变化、是否重复发生 |
| 事实与推测容易混淆 | Agent 输出必须区分观察事实、推断假设和处置建议 |
| 历史经验未沉淀 | 同类失败如果每次从头查，Agent 无法真正积累运维知识 |

## 3. 用户已经表达的工作倾向

以下表述用于继续讨论，不等同于最终产品定义。

### 3.1 不做 Text2SQL

理由：

- 当前数据量、表数量和血缘复杂度不足以证明需要通用 Text2SQL；
- 项目已经有指标字典、查询表和固定口径，自由生成 SQL 反而降低确定性；
- Agent 可以查询指标，但不需要把“自然语言转任意 SQL”作为核心能力。

### 3.2 不做执行型运维

- Agent 不应承担重跑、修复、补数、回滚等动作；
- 这些动作具有状态变更、幂等性、影响范围、审批和回滚风险；
- 当前不把 shadow execution 作为需求；
- 即使未来考虑实验空间，也不应成为当前 Data Agent 设计的基础。

### 3.3 名称和路线优先考虑成熟实践

- 不为了标新立异强行创造新类别；
- DataOps Agent 本身没有被限定为“必须执行动作”；
- 应优先研究市面成熟示例，判断哪些概念和实践可以复用；
- “诊断型”与“DataOps”不是二元对立，最终名称和范围应依据实现难度、成熟案例和项目契合度决定。

### 3.4 可信度结论是参考，不是真相

- Agent 对“数据能不能信”的判断可能有误；
- Agent 输出应作为参考和解释层；
- Gate、数据事实和人工确认仍承担最终判定责任；
- 是否纳入日常可信度问答，应依据实现可行性和难度评估。

### 3.5 Agent 需要哪些数据暂后置

- 具体读取 Airflow、Spark、DWD/DWS、ODS 日志还是基础设施状态；
- 哪些数据通过结构化契约读取；
- 哪些异常需要只读诊断探针；

以上问题留到后续链路和 Agent 能力开发讨论。

### 3.6 失误与工作记录应持久化

用户当前倾向：

- “失误记录”和“工作记录”值得持久化；
- 即使记录可能引入幻觉、过期信息或被错误引用，仍认为收益大于风险；
- 如何隔离权威数据与 Agent 自身记录，是后续需要讨论的问题。

## 4. 当前候选定位

### 4.1 共同认识

无论最终叫什么，当前讨论中的 Agent 更接近：

> 位于数仓主链路之外，读取运行、质量和诊断证据，帮助人理解批流不一致、任务失败和数据可信度的只读分析 Agent。

### 4.2 名称候选

| 候选 | 潜在优势 | 潜在风险 |
|---|---|---|
| DataOps Agent | 与成熟实践容易对齐，可复用概念多 | 容易被误解为执行型运维 |
| 数仓可靠性诊断 Agent | 明确强调诊断和可信度 | 听上去可能弱化 DataOps 的流程特征 |
| Data Incident Copilot | 贴近事故分析场景 | 弱化日常可信度查询和历史记录 |

当前**不选定名称**。后续应结合成熟项目和实际功能范围比较。

## 5. 功能边界候选

### 5.1 可能包含

- 批作业失败分诊：判断失败发生在哪一层；
- Gate 结论解释：为什么 pass、限制、等待或阻断；
- 批流对账差异性质分析；
- 当前运行与最近正常运行的对比；
- 事故证据时间线整理；
- 可能原因排序与反证条件；
- 只读排查步骤建议；
- 历史相似事故检索；
- 指标口径、限制和可信范围解释。

### 5.2 当前明确不包含

- 任意 Text2SQL / 自由生成查询；
- 重跑、补数、修复、回滚；
- 修改 Gate 阈值、指标口径或契约版本；
- 直接修改数仓、Kafka、Redis、Airflow 或生成器状态；
- 自动替人发布、阻断或做业务决策；
- 把推断内容伪装成已验证事实。

## 6. 读写边界候选

### 6.1 读取层级

| 层级 | 候选内容 | 状态 |
|---|---|---|
| R0 | `metric_dict`、`partition_status`、`run_manifest`、Gate 报告、契约版本 | 已有结构化产物 |
| R1 | Airflow DAG/task、Spark application、运行时间、重试、退出码 | 待讨论 |
| R2 | DWD/DWS 有界探测、空表、分区存在性、行数、异常样本 | 待讨论 |
| R3 | Airflow / Spark / JVM / 容器日志 | 待讨论 |
| R4 | Kafka、Redis、SeaweedFS、网络与资源状态 | 待讨论，可能超出首期 |

需要特别讨论：任务在 Gate 前失败时，R0 可能不完整；完全不读取运行层证据，Agent 难以覆盖用户提出的核心痛点。

### 6.2 写入边界

当前讨论中的原则：

- 不写任何权威数仓表；
- 不写 Gate 结论；
- 不写 Airflow 控制状态；
- 不触发执行动作；
- Agent 自身的事故分析和工作记录可以持久化，但必须与权威数据明确隔离；
- Agent 记录不得反向成为 Gate 或业务指标的事实来源。

## 7. 链路角色候选

Agent 不是批流数仓的关键路径组件：

```text
Generator → Kafka → ODS → DWD/DWS/Tier0
                         │
                         ▼
                        Gate
                         │
              manifest / partition_status / reports
                         │
                ┌────────┴────────┐
                ▼                 ▼
              看板/人工       Agent 只读分析
                                     │
                                     ▼
                              诊断、解释、建议
```

候选角色：

- 主链路旁路消费者；
- Agent 不可用不影响数仓运行；
- Agent 输出不成为下游计算依赖；
- Airflow 负责执行，Gate 负责判定，Agent 负责解释和引导排查。

## 8. 开放问题

1. 最终名称采用成熟 DataOps 概念，还是采用更精确的可靠性/诊断描述？
2. 首期重点是事故诊断，还是同时覆盖日常“数据能不能信”的解释？
3. 任务在 Gate 前失败时，Agent 需要哪些运行元数据和日志证据？
4. 明细数据采用自由查询还是固定只读诊断探针？
5. Agent 工作记录应保存哪些内容，如何区分事实、推断、建议和最终人工结论？
6. 如何评估 Agent 的诊断正确性、引用完整性和幻觉率？
7. 如何检索历史事故，同时避免过期记录误导当前判断？
8. Agent 与现有 Gate、Airflow、看板、语义层之间的权威关系如何保持清晰？

## 10. 候选技术架构（2026-10-27 补充，非定案）

### 10.1 讨论基线

当前更完整的架构候选不是单一的 LangGraph 或 Neo4j，而是：

```text
Web / CLI / Alert
        │
        ▼
FastAPI
        │
        ▼
LangGraph：问题路由 / 证据计划 / 校验 / 假设 / 报告
        │
        ├─ 精确工具：Delta / DuckDB / Airflow / Spark / Logs
        └─ 历史知识：Neo4j / 全文 / 向量 / 人工记录
        │
        ▼
结构化诊断报告 + 工作记录
```

候选分层：

| 层 | 候选技术 | 作用 |
|---|---|---|
| API | FastAPI + Pydantic | Agent 服务、请求校验、流式输出 |
| 工作流 | LangGraph | 问题路由、状态机、分支、重试、人工补充 |
| 图与关系 | Neo4j | 血缘、事故、证据、假设、工作记录关系 |
| 工作流状态 | PostgreSQL；本地早期可 SQLite | checkpointer、会话、事故生命周期 |
| 轻量数据探测 | DuckDB + pyarrow / deltalake | 无需启动 Spark 的只读检查 |
| 数仓事实 | 现有 Delta Lake / Spark | 指标、分区、明细与对账真值 |
| 调度事实 | Airflow REST API | DAG/task 运行状态、重试、日志入口 |
| 文档与报告 | SeaweedFS / S3 | Gate 报告、日志切片、事故复盘、附件 |
| 模型接入 | OpenAI-compatible 抽象 | 避免绑定单一模型供应商 |
| 观测 | LangSmith / Langfuse / OpenTelemetry 候选 | 节点、工具、token 与失败追踪 |
| 测试 | pytest + incident fixtures | 故障分类、证据引用和诊断回归 |

以上技术栈仍是候选组合，不代表已经引入 PostgreSQL、DuckDB 或向量索引。

### 10.2 为什么讨论 DuckDB + Delta

DuckDB 与 Delta 结合，首先解决的不是“批流一致性计算”，而是：

> **Agent 如何低成本、只读地检查同一份数仓事实，而不必为每个问题启动 Spark。**

候选价值：

1. **沿用既有事实源**：直接读取 Delta 或 Delta 对应的 Parquet 数据，不把数仓重新复制进 Agent 数据库；
2. **降低探针成本**：查分区是否存在、行数、空值、重复量、时间范围和小样本时，可以避免 Spark 启动与容器调度开销；
3. **适合交互式诊断**：一个失败问题通常需要多次小范围检查和比较，轻量查询引擎更适合这种节奏；
4. **便于固定读取版本**：分析某次 Run 时应绑定 Delta 版本或时间点，避免一边排查一边读到后续写入；
5. **支持本地分析生态**：DuckDB、Arrow、parquet 与 Python 工具链连接自然。

需要明确的限制：

- DuckDB **不是批侧真值计算器**，不能替代 BatchApp、DWS 构建或 V-01/V-02；
- 不适合大范围扫描、复杂 Spark 语义或高并发；
- 读取 Delta 时需关注事务快照、时间旅行和读写并发一致性；
- 如果 Agent 自己复制一套指标 SQL，会重新引入口径漂移；
- 轻量探针只能回答“现场数字是什么”，不能自行宣布“批流计算错误”。

因此 DuckDB 的合理候选角色是 **只读证据探针**，而不是第二个数仓引擎。

### 10.3 为什么讨论 Neo4j 检索

Neo4j 进入讨论，主要是因为事故诊断具有天然的多跳关系：

```text
Run → Task → Dataset → 上游 Dataset
Incident → Evidence → Hypothesis
GateResult → Dataset
WorkRecord → Incident
HistoricalCase → Similar Evidence / Different Root Cause
```

候选检索方式：

1. **精确图遍历**：当前 Run 的失败节点、上下游、相关 Gate、受影响分区；
2. **全文/标识符检索**：按 run_id、gate_id、表名、指标编号；
3. **向量检索**：历史事故叙述、人工复盘和 Runbook；
4. **图扩展**：向量召回后补充相关事故、证据、解决记录和同类失败；
5. **混合检索**：元数据过滤 + 全文 + 向量 + 图扩展，最后可选 rerank。

但“所有检索都由 Neo4j 承担”不是必然结论：

- Neo4j 更适合关系遍历；
- 全文与向量可以放在 Neo4j，也可以使用独立检索组件；
- 当前知识索引尚未设计，过早确定检索存储会反向限制文档与事故记录模型；
- 当前事故事实必须走结构化精确查询，不能靠 RAG 猜测。

### 10.4 当前技术方向判断

最可能的候选方向是：

```text
LangGraph 管工作流
Neo4j 管关系与历史上下文
Postgres 管工作状态
Object Storage 管原始报告与文档
Delta / Airflow / Logs 作为事实源
DuckDB 作为轻量只读探针
RAG 作为历史经验与潜在纠错机制
```

该组合目前只是讨论基线，后续仍需根据 Agent 功能和数据范围裁剪。

## 11. 历史案例的作用

### 11.1 用户初步判断

> 历史案例的主要作用应当是提供纠正现有结果潜在错误的可能性。

这个判断与“历史案例仅用于参考过去怎么解决”不同，重点在 **纠错与反证**。

### 11.2 候选理解

历史案例可能承担以下作用：

- 当前 Agent 已形成初步结论后，检索相似历史事故，检查是否有不同根因；
- 查找“症状相似但结论曾经错误”的案例；
- 提醒当前诊断可能遗漏的证据；
- 提供已有反例，降低过早收敛到单一假设的风险；
- 在用户追问时补充历史解决经验，但不直接替代当前事实。

因此，RAG 的候选定位可以是：

> **先支持当前证据链，再挑战当前证据链。**

历史案例不能覆盖当前 Run 的事实，也不能因为“以前是某原因”就推断“这次也是同一原因”。

### 11.3 尚待讨论

- 如何从历史案例中检索“不同根因”而不是只检索语义相似；
- 未验证案例是否可以进入纠错检索；
- 历史案例如何标记适用版本、数据范围和失效条件；
- Agent 如何表达“历史案例提示当前结论可能错误”，而不制造新的伪因果。

## 12. “分诊”是什么

“分诊”在此处不是复杂的自治 Agent，也不是医疗语义，而是：

> **在开始取数和分析前，先判断用户当前问的是哪类问题，并选择对应的证据路径。**

候选问题类型：

| 类型 | 示例 | 首要证据 |
|---|---|---|
| 当前事故 | 凌晨为什么失败 | Airflow、Spark、日志、Run |
| 数据可信度 | 10-18 的 DWS 能不能用 | Gate、partition_status、manifest |
| 批流差异 | V-02 为什么不是 0 | 快照、V-02、口径版本、输入 |
| 历史经验 | 以前类似问题怎么查 | 历史案例、Runbook |
| 指标解释 | 为什么这个指标这么算 | 指标字典、口径 |
| 信息不足/越界 | 缺少运行标识或要求执行动作 | 追问或拒答 |

它可以只是一个分类节点、规则路由或少量 LLM 分类，不一定需要独立工作流。

分诊的主要目的：

- 防止所有问题都进入 RAG；
- 防止历史经验先于当前事实；
- 明确哪些问题需要运行元数据、哪些只需要 Gate、哪些只需要文档；
- 明确 Agent 是否缺少足够证据。

## 13. 工作记录与人工确认

“人工确认”不应理解为要求人持续盯守。

候选方式是：

- Agent 自动保存事实、工具调用、证据、假设和报告草稿；
- 记录默认标记为 `machine_generated/unverified`；
- 人不必持续审核；
- 当人工主动修正、补充或确认时，再记录 `human_verified`；
- 历史检索可以按可信级别过滤，而不是强迫所有记录先人工审核；
- 未确认记录仍可帮助排查，但不能被描述为已确定经验。

这样可降低个人项目的人工负担，同时保留记录可信度差异。

## 14. 知识索引暂后置

当前不设计知识索引的最终形态。先保留以下约束：

- 当前事故事实与历史知识必须分开；
- 原始文档和报告应保留来源、时间、Run、契约版本与可信级别；
- 后续再决定全文、向量、图扩展分别使用什么存储；
- 在知识索引设计前，不把历史案例纳入权威结论链路。
